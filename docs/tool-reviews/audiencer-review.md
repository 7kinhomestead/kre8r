## Verdict: Dashboard, not yet a worklist — but the gap is small and well-scoped.

As it stands today AudiencΩr is **a dashboard that shows data without enabling action.** Every interactive affordance on the Community tab is read-only: warm leads, score movers, and the event feed all render counts and pills with no buttons. The PATCH endpoint to act on a lead exists but is never invoked. The creator's daily loop dead-ends at "I can see who to DM" with no way to draft, send, or close it inside the tool — they must leave for Kajabi and hand-write everything.

It is **not actually useful for daily community management yet**, and worse, two high-severity bugs mean the data it *does* show is quietly unreliable: the most important event type never fires after backfill (AUD-1), and a harmless re-sync poisons the movers table (AUD-3).

**But** this is a near-miss, not a wrong architecture. The data model, sync pipeline, tier logic, warm-lead detection, and the very PATCH endpoint needed for action all already exist — the tool stops one UI layer short of being the worklist it was designed to be. The path from "report" to "most useful non-filming tool" is concrete and short:

## Findings (12 total)
### [HIGH] first_post event never fires for existing lurkers — the core graduation signal is dead
**bug** | C:\Users\18054\kre8r\src\routes\community.js:67-71
In src/routes/community.js the first_post event is only pushed `if (!existing && m.posts_count > 0)` — i.e. only for members who are BRAND NEW to the DB and already arrive with posts. The community strategy (CLAUDE.md) is built entirely around 1,332 lurkers at progress_score 25 who have never posted. After the first sync ingests all 1,357 greenhouse members, every one of them is `existing` forever. When a lurker later posts for the first time, `existing` is truthy so no first_post event is ever logged. The single most important moment in the whole AudiencΩr strategy — a lurker breaks silence — is invisible. The Recent Events feed will therefore essentially never show a first_post after the initial backfill.
**Fix:** Detect first post via delta, not novelty: `if (existing && existing.posts_count === 0 && m.posts_count > 0)` (plus the new-member case). Compare against the prior synced posts_count, which is available from db.getCommunityMember(m.id). This makes 'first post' fire the week a real lurker graduates, which is the event Jason actually wants to react to with a DM.

### [HIGH] Warm-lead DM workflow has no UI — leads pile up at 'draft' forever
**workflow-order** | C:\Users\18054\kre8r\public\audience.html (loadWarmLeads) + src\routes\community.js:200 (PATCH wired but unused)
The whole point of warm leads is: detect engaged Greenhouse member -> draft a DM -> Jason sends it -> mark outcome. The PATCH /api/community/warm-leads/:id endpoint exists (dm_status, outcome, outcome_at) and updateWarmLead supports it, but audience.html never calls it. loadWarmLeads() renders each lead read-only with a status pill but no buttons to approve, mark sent, or record an outcome. There is also no 'draft DM' generation anywhere — dm_draft is only ever null unless an MCP session writes it. So the creator's daily workflow dead-ends: they can SEE warm leads but cannot act on them inside the tool, cannot dismiss a bad lead, and cannot stop a converted/declined lead from reappearing every week. This is the single biggest gap to making AudiencΩr the 'most useful non-filming tool' — it surfaces work but doesn't let you close the loop.
**Fix:** Add per-lead action buttons in loadWarmLeads(): 'Draft DM' (Claude writes a Garden-tier invite in Jason's voice via src/utils/claude.js, saved to dm_draft), 'Copy & Mark Sent' (PATCH dm_status='sent', dm_sent_at), and 'Outcome: Joined / Not yet / No' (PATCH outcome). Filter the default warm-leads list to status!='no' and outcome IS NULL so handled leads drop off. This turns the tab from a passive report into the actual daily driver.

### [HIGH] Running the sync twice in one day duplicates history rows and corrupts score movers
**bug** | C:\Users\18054\kre8r\src\db.js:6400-6407 and 1572-1583 (no unique constraint); insert at src\routes\community.js:95-101
POST /sync calls insertCommunityMemberHistory for every member with snapshot_date = today. The community_member_history table has only a NON-unique index on (member_id, snapshot_date) and the insert is a plain INSERT (db.js:6400-6407). If the weekly snapshot is run twice on the same date (easy to do from Claude Desktop — re-run after a partial pull, or a retry), every member gets a second row for that date. detectScoreMovers() (db.js:6420-6439) joins history rows on the two MAX distinct snapshot_dates; duplicate same-date rows produce a self-cartesian join, yielding duplicated/garbage mover entries and, on the very first double-run, no valid 'previous' date at all. The Prime Directive is 'never lose the thread' — here a benign re-run silently poisons the week's movers data.
**Fix:** Add UNIQUE(member_id, snapshot_date) to community_member_history (in BOTH bootstrapTenantTables and runMigrations per the CLAUDE.md dual-path rule) and change insertCommunityMemberHistory to INSERT ... ON CONFLICT(member_id, snapshot_date) DO UPDATE. Makes re-running a sync idempotent.

### [HIGH] Data is only as fresh as the last manual MCP session — no staleness guard or auto-sync
**improvement** | C:\Users\18054\kre8r\public\audience.html (communityLastSync render) + src\routes\community.js:/health
Every number in AudiencΩr (tier counts, lurkers, warm leads, movers) comes from a weekly Claude-Desktop MCP push to /sync. There is no scheduled/automated sync and no visual staleness warning. communityLastSync just prints the snapshot_date with no 'X days ago / STALE' treatment. If Jason forgets to run the snapshot for 3 weeks, the dashboard confidently shows 3-week-old data as if it were current, and warm-lead 'days ago' counters (computed from warm_leads.created_at) drift out of sync with reality. For a tool the creator is supposed to live in during non-filming time, silently-stale data violates 'is the community data accurate and actionable?'.
**Fix:** Compute age from latest_snapshot.snapshot_date and badge it: green <8d, amber 8-14d, red >14d with 'Data is N days old — run the weekly snapshot'. Longer term, expose a cron/scheduled-task that triggers the MCP pull (or at minimum a prominent 'last successful sync' health indicator) so the creator is never reasoning on stale numbers.

### [MEDIUM] Tier counts in /sync are computed before tier-correct, so paid tiers are usually wrong until a second call
**bug** | C:\Users\18054\kre8r\src\routes\community.js:104-118 (snapshot written from pre-correction counts); tier-correct at :246-300 does not re-upsert snapshot
Per CLAUDE.md, list_members has NO tier info — tiers live as CRM tags and are reconciled via the separate POST /tier-correct (match by email). But /sync computes counts via getCommunityMemberCount() (which groups by community_members.tier) and writes them into the snapshot immediately. Unless the MCP session also passes founding50_ids/garden_ids INTO the sync body (the code supports it but the documented snapshot process at CLAUDE.md does not include them), every synced member defaults to tier='greenhouse' (db.js:6333) and the snapshot records founding50_count/garden_count = 0 / near-0. The health strip then shows Garden and Founding 50 as 0 or stale until /tier-correct runs — and even then the snapshot row already persisted with the wrong numbers (tier-correct updates members but does not rewrite the snapshot). Result: the paid-tier KPIs Jason most cares about (revenue tiers) are the least reliable numbers on the page.
**Fix:** Either (a) require founding50_emails/garden_emails in the /sync payload and apply tier correction before computing counts, or (b) have /tier-correct re-run getCommunityMemberCount() and upsertCommunitySnapshot() for today so the snapshot reflects corrected tiers. Document whichever in the CLAUDE.md snapshot steps.

### [MEDIUM] Two loops over members in /sync can be merged; history insert duplicates the member walk
**simplification** | C:\Users\18054\kre8r\src\routes\community.js:56-101
POST /sync iterates `for (const m of members)` to upsert members + build events (lines 56-92), then immediately iterates `for (const m of members)` AGAIN (lines 95-101) only to call insertCommunityMemberHistory. With ~1,366 members this is two full passes plus N individual INSERTs outside any transaction — every insert is its own implicit commit, which is the slow path in better-sqlite3 and noticeably lengthens the sync. The events insert loop (line 104) and warm-lead loop add more separate writes.
**Fix:** Merge the history insert into the first member loop, and wrap the whole sync body in a single better-sqlite3 transaction (db.transaction(...)). One pass, one commit — large correctness and speed win for a 1,366-row push, and it makes the whole sync atomic (partial failures don't leave half-written snapshots).

The pipeline diagram has community health feeding NorthΩr/VectΩr for strategy, but the most actionable per-member output (a ready-to-send DM) is orphaned.
**Fix:** Add a 'Generate Garden invite' action on each warm lead that calls the Claude caller with the lead's signals + Jason's voice calibration, stores result in warm_leads.dm_draft, and offers copy-to-clipboard (Kajabi send_dm is MCP-only, so copy is the realistic path). ### [MEDIUM] getAllCommunityMembers default limit 500 silently caps warm-lead candidate scan
**bug** | C:\Users\18054\kre8r\src\routes\community.js:124 + src\db.js:6346
The warm-lead detection in /sync calls db.getAllCommunityMembers({ tier:'greenhouse', min_score:50, max_score:99 }) with no limit, so it inherits the default LIMIT 500 (db.js:6346). Today the 50-99 score band is small so this is harmless, but the community game strategy is explicitly designed to push the 1,332 lurkers UP from score 25. As that succeeds, the 50-99 greenhouse band will grow past 500 and warm-lead detection will silently stop scanning the overflow — exactly when the strategy is working best. A scan that quietly drops candidates is an accuracy bug waiting to trigger.
**Fix:** Pass an explicit high limit (e.g. limit: 100000) for the warm-lead scan, or have detection paginate. Don't rely on the 500 default for a full-population scan.
