# ComposΩr Review — Synthesis

## TOP 3 BY CREATOR IMPACT

**1. "Generate Music" silently destroys all selections and uploaded MP3 references (Prime Directive violation).**
`POST /generate/:project_id` unconditionally calls `db.deleteComposorTracksByProject(projectId)` before writing fresh prompt-only rows. The button stays enabled the whole time. If Jason spends a non-filming day picking tracks per scene and uploading his own MP3s, one accidental click wipes every `selected` flag and `public_path` — the MP3 files survive on disk but their DB rows (and the curation) are gone, with no recovery path. This is exactly the "if this goes wrong right now, what does the creator lose" scenario the Prime Directive exists to prevent, and it lands on the very workflow (non-filming-day curation) Jason says he wants to live in.
*Fix:* guard the delete behind a force-flag + confirm when any track has `selected=1` or non-null `public_path`; relabel the button to "Regenerate (clears selections)" once tracks exist. (findings composor-2, comp-5)

**2. The entire SSE progress contract is broken three ways — the creator watches a frozen, blank UI during the slowest operation in the app.**
Three independent defects compound: (a) backend emits flat `{stage:...}` objects but `streamJob()` branches on `msg.type` (`'progress'/'event'/'done'/'error'`) which never exists, so every branch is skipped; (b) even reading `.stage`, `formatStageLog()` switches on a stale vocabulary (`track_saved`, `suno_downloaded`, `all_done`) that doesn't match the emitted stages (`analyzing_scenes`, `track_ready`, `credits_exhausted`, `suno_skipped`); (c) `updateStatusBar`/`loadTracks` read `d.state` but the API returns `composor_state`, so the state pill always shows "idle" and auto-poll never restarts on reload. Net: 0% bar, empty log, tracks don't appear as they finish, no success/failure/credits-exhausted signal. During a multi-minute Suno run this looks frozen — the creator re-clicks or assumes failure. (findings composor-sse-shape-mismatch, composor-formatstage-stage-names-mismatch, composor-statusbar-state-key, composor-3, comp-7, comp-8)

**3. Every DaVinci push with a CTA crashes — the headline "one click to DaVinci" feature is dead in the common case.**
The `import-to-davinci` route appends `--cta_timestamp` to the `place-music.py` spawn whenever a CTA cut exists, but the script's argparse only declares `--project_id/--project_name/--tracks_json/--fps`. An unrecognized arg makes argparse exit code 2, and `proc.on('close')` fails the job with "place-music.py exited 2." Since the feature is advertised around a Fairlight CTA marker (and the script has no code to place one anyway), the push always fails for any project with a CTA. (finding composor-davinci-cta-arg-crash)

## WORKFLOW ORDER VERDICT — ComposΩr BEFORE ClipsΩr

**ComposΩr must come before ClipsΩr.** This is unambiguous across three converging sources of truth:

- **Doc:** CLAUDE.md defines post-production as AssemblΩr → ReviewΩr → **ComposΩr → ClipsΩr**.
- **Data dependency:** ComposΩr reads the `cuts` table (CTA timestamp, social-clip ranks, overall_notes from ReviewΩr/CutΩr), scores the *full long-form* video, and places one MP3 per scene sequentially on DaVinci's `04_AUDIO` timeline of the master edit. ClipsΩr then carves short social clips *out of* that finished, scored master. You score the film, then cut clips from it — scoring is a whole-video act that is meaningless to do per-clip after extraction.
- **The tool's own UI:** composor.html hardcodes a "→ Continue to ClipsΩr" advance button (`goClipsrBtn`), proving its author intended ComposΩr to come first.

**The nav is wrong.** `public/js/nav.js` line 60-61 renders ClipsΩr *then* ComposΩr — placing ComposΩr last in the post block. A creator following the nav would cut social clips from un-scored footage, then have to re-cut after the score exists: exactly the redundant decision the Secondary Directive forbids, and consistent with Jason's complaint of "tools I want to use but can't." **Fix is a one-line array reorder, zero backend risk:** VaultΩr → AssemblΩr → ReviewΩr → **ComposΩr → ClipsΩr** → BrollΩr → AnimΩr → CleanΩr. (findings composor-nav-order-reversed, composor-1, composor-01, comp-1)

## ComposΩr's TRUE ROLE — and whether the implementation serves it

**Stated role:** the "final video composition phase — assembling the final video with music, graphics, title cards, and other compositional elements." It is meant to be the *composition desk*: the sit-down, no-camera-required work that turns a beat-mapped assembly into a finished film, and the natural home for Jason's non-filming days.

**Does the implementation serve it? Partially — it delivers one quarter of the mission and is fragile even there.**

- **Music is built, but brittle:** scene analysis → Suno prompts → MP3 → DaVinci `04_AUDIO`. Working, but undermined by the destructive regenerate (Top 3 #1), the broken progress UI (Top 3 #2), the CTA crash (Top 3 #3), and placement that uses Claude's *estimated* cumulative durations rather than the real `cuts` timestamps it already reads — so music drifts on the timeline and `AppendToTimeline` ignores the computed `start_frame` entirely, silently desyncing markers from audio (composor-place-tracks-cursor-desync, composor-05).

- **The graphics half is entirely absent.** No title cards, no lower-thirds/name supers, no intro/outro bumpers, no chapter cards, no end-screen CTA card — the "graphics and title cards" half of its own stated mission doesn't exist. This is the single highest-leverage gap: on a non-filming day there is currently *nothing to do* in ComposΩr but wait on Suno. A `graphics-writer.js` that reads the same selects+cuts payload to propose editable title/chapter/lower-third/end-screen cards (tied to cut timestamps, pushed into DaVinci via the existing spawn pattern) would turn it into the real composition desk and give Jason substantive desk work. (finding composor-5)

- **Integration is a dead end.** ComposΩr's output terminates inside Resolve — no downstream tool (ClipsΩr, PostΩr) reads the score; the render-back-out is a manual off-app step with no `scored_at` state to keep the thread visible across the ComposΩr→ClipsΩr boundary. (finding composor-02)

**Verdict:** ComposΩr is correctly *positioned* (before ClipsΩr) but currently *mis-placed in nav* and *under-built* — it is an AI music-scorer wearing a composition-desk label. To serve its true role it needs (a) the nav reorder, (b) the three reliability fixes above, and (c) the missing graphics/title-card half that justifies its name and makes it a genuine non-filming-day home.

**Lower-priority but real:** dead/broken `POST /select/:track_id` route querying project_id 0 (delete it — composor-4/03/comp-3); in-memory `jobs` Map leaks and orphans runs on the 5-min Electron restart, leaving `composor_state` stuck at 'generating' with a never-terminating poll loop (composor-jobs-map-unbounded, composor-8/comp-9); inline `fetch` in scene-analyzer.js/prompt-writer.js bypassing the mandated `src/utils/claude.js` and hardcoding "7 Kin Homestead" (Engine-vs-Soul violation — comp-6); no auto-select of a default variation (15-21 auditions before any forward progress — comp-2); and `downloadFile` writing non-200/redirect bodies as valid-looking corrupt MP3s (composor-download-redirect-leak).

### [CRITICAL] Frontend SSE handler expects {type,data} envelope; backend sends raw {stage} objects
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\composor.html streamJob() (es.onmessage, ~'if (msg.type === ...') vs C:\Users\18054\kre8r\src\routes\composor.js pushEvent/finishJob/failJob
**Problem:** The backend SSE producer (pushEvent/finishJob/failJob in composor.js) pushes raw event objects with a `stage` field, e.g. {stage:'analyzing_scenes'}, {stage:'done', result}, {stage:'error', error}. sseStream() writes them verbatim. But the frontend streamJob() in composor.html only reacts to msg.type === 'progress' | 'event' | 'done' | 'error'. None of these envelope keys exist on the emitted objects, so EVERY branch is skipped: the progress bar never advances, formatStageLog() is never called, loadTracks() is never re-triggered on track_ready, and the onDone callback only fires via the es.onerror fallback when the server closes the stream. The user watching Generate Music or Push to DaVinci sees an empty COMPOSING log and a 0% bar for the entire run, with no indication of success, failure, or credits-exhausted. This is the central state-visibility break in the whole module.
**Fix:** Make the two ends agree on one envelope. Either wrap server events as {type:'event', data:ev} (and {type:'done'/'error'}) in sseStream/finishJob/failJob, OR rewrite streamJob to read d.stage directly: treat stage==='done' as completion, stage==='error' as failure, and pass every other event to formatStageLog. Given finishJob already emits {stage:'done', result} and failJob {stage:'error', error}, the smallest fix is changing the frontend to branch on msg.stage instead of msg.type.

### [HIGH] In-memory jobs Map is never cleaned up — leak, and lost on restart kills active SSE
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\routes\composor.js jobs Map / createJob / finishJob / failJob (no TTL or delete)
**Problem:** jobs = new Map() grows forever: createJob() adds entries on every generate and every davinci push, and nothing ever deletes them. Each holds full event arrays and an EventEmitter. Over a long-running Electron/pm2 session this leaks unbounded memory. Worse for the Prime Directive: jobs live only in process memory, so a server restart (the 5-min Electron backup cycle, a crash, or a deploy) during a generation orphans the job — the SSE reconnect to /status/:job_id returns 404 'Job not found', the frontend EventSource hits onerror and silently fires onDone with no error shown, and the user has no recovery path to see whether generation finished. Tracks may still be written to DB by the detached async IIFE, but the UI gives no signal.
**Fix:** Delete or expire jobs after completion (e.g. setTimeout(()=>jobs.delete(id), 5*60*1000) in finishJob/failJob), and on /status 404 have the frontend fall back to polling /tracks so the creator can still recover the result after a restart.

### [MEDIUM] AppendToTimeline ignores computed start_frame; skipped/failed clips silently desync all later scene placements
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\scripts\davinci\place-music.py place_tracks() (~line 136-215): start_frame computed but AppendToTimeline lacks recordFrame

**Fix:** Add a 'recordFrame': start_frame entry to clip_info so DaVinci places at the intended position, or stop advancing the cursor for skipped clips and document that placement is purely sequential. Also surface ok:false to the job result when failed_count>0 instead of always returning ok:true.
