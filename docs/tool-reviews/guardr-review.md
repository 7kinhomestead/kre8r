# GuardΩr — Architectural Review
*Opus audit.*

## Synthesis
All load-bearing claims confirmed: `match_confidence * 100` bug (markr.js:341), `overall_confidence` on 0-100 scale (detect.js:291), watcher has zero markr/guard references, `downloadToTmp` defined but never called, empty-fingerprint early-returns, and guard /submit only runs detection on `uploadedFile` (line 150-151), never on `submitted_url`.

GuardΩr — Synthesis

Top 3 (ranked by what actually breaks the creator's trust):

1. GUARD-1 (high) — The engine is cold by default. Fingerprinting is on-demand only; there's no watcher hook, no cron, no background catch-up. With empty fingerprint tables every detection early-returns confidence 0 (`detect.js:83,160`), so a genuine stolen-clip report files cleanly as verdict "none." The feature *looks* like it works while the detection that justifies it never fires. This is the structural no-op.

2. GUARD-4 (medium, but cheap + legally visible) — Scale mismatch corrupts the one external artifact. `overall_confidence` is 0-100 (`detect.js:291`), but the DMCA builder does `report.match_confidence * 100` (`markr.js:341`). An 85% match prints "8500%" into the notice that goes to a platform's legal team. One-line fix, outsized credibility cost. Confirmed verbatim in code.

3. GUARD-2 (high) — Watermark layer is structurally incapable of a true positive. `detectWatermark` correlates against a constant 128 with no reference frame, so it tracks scene brightness, not the ±1 watermark delta — and `watermarkVideo` is never invoked anywhere, so no footage carries a mark to detect. Yet it's weighted 20% of the verdict (`detect.js:289`). It can only manufacture false confidence; it should be zeroed until validated against real watermarked-vs-clean samples.

(Honorable mention: GUARD-5 — link-only fan reports, the *common* case, run no detection at all because `/submit` only processes `uploadedFile`, never `submitted_url`; `downloadToTmp` exists but is dead code. Reinforces GUARD-1's "looks processed, isn't" theme.)

Verdict: Not yet earning its place. GuardΩr today is a report intake form wearing a detection engine's clothes. Against the Prime Directive's lens — *if this goes wrong, what does the creator lose?* — the failure mode is the worst kind: silent false confidence. Jason sees filed reports and a public "violations caught" counter (GUARD-6) and believes he's protected, while the engine is cold (GUARD-1), the most common submission type is never analyzed (GUARD-5), one of three layers can only lie (GUARD-2), and the legal output is numerically garbled (GUARD-4). It doesn't lose creative state, but it loses something arguably worse for a straight-talking brand: it quietly tells him a comforting untruth.

It earns its place only after: (a) auto-fingerprinting wired into the vault intake pipeline so the engine is warm, (b) `submitted_url` detection actually wired through, (c) the watermark layer dropped from the weighting until calibrated, and (d) the DMCA scale fixed. (a) and (b) are the difference between a working tool and a placebo; (c) and (d) are cheap correctness. Until (a)+(b), recommend not promoting the public guard.kre8r.app page — an unauthenticated, unthrottled, synchronous-ffmpeg endpoint (GUARD-3) backed by a no-op detector is net-negative exposure.

## Findings (6 total)
### [HIGH] Detection DB is empty unless Jason manually fingerprints the vault — every fan report silently scores 0
**workflow-order** | src/markr/detect.js:80-87,158-164; src/routes/markr.js:39-109; src/vault/watcher.js (no integration); server.js:1071-1129 (schedulers, none for markr)
GuardΩr's whole value proposition is matching a fan-submitted repost against Jason's originals. But fingerprinting is purely on-demand: it only runs when someone POSTs to /api/markr/fingerprint-vault or /fingerprint/:id. There is NO background worker, NO watcher integration (watcher.js has zero markr/guard references), and NO cron registration in server.js (only postor queue, vectr-auto, and morning-sync schedulers exist). So compareByPHash/compareByAudio early-return {match:false,confidence:0} when getAllVideoFingerprints()/getAllAudioFingerprints() are empty — which they are by default. A fan submits a genuine stolen clip, detection returns verdict 'none', confidence 0, and the report looks like a non-match. The tool appears to work (report is filed) but the detection that justifies it never fired. This is the single biggest reliability gap: the feature is structurally a no-op until a manual batch job is run, and nothing reminds Jason to run it or re-run it as new footage lands in the vault.
**Fix:** Wire fingerprinting into the vault watcher/transcribe pipeline so new footage is auto-fingerprinted on intake (mirroring how frame-analysis-queue works), OR add a periodic catch-up job using getUnfingerprintedFootage() as the idempotency cursor (it already exists). At minimum, surface vault fingerprint coverage on the inbox UI ('0 of N originals fingerprinted — detection will not work') so Jason knows the engine is cold. Without one of these, GuardΩr does not earn its place — it generates filed reports with no detection backing.

### [HIGH] Watermark detector correlates against a fixed neutral 128, not the original frame — produces brightness-driven false confidence
**bug** | src/markr/watermark.js:254-286 (detectWatermark), aggregated in src/markr/detect.js:226-249,285-291
detectWatermark() computes confidence as correlationSum += (luma - 128) * expected over sampled pixels, then confidence = (avgCorr/1.5)*100 with match at >=60. This has no reference to the original (un-watermarked) frame. The (luma-128) term is dominated by actual scene brightness, not the +-1 watermark delta: a bright clip (lots of luma>128) inflates correlation toward a false positive, a dark clip deflates it toward a false negative. The real watermark signal is +-1 luma — utterly swamped by content that ranges 16-240. The 60 threshold is asserted 'empirically (avgCorr ~0.3-1.5)' in a comment, but uploads/guard/ is empty (zero real submissions) and watermarks table is unused, so there is no calibration behind it. As written, Layer 3 is not a trustworthy positive signal; it is noise weighted at 20% of the overall verdict.
**Fix:** A spread-spectrum watermark can only be recovered by comparing against the original frame (or a high-pass/local-mean-subtracted residual), not a global constant 128. Either (a) subtract a local neighborhood mean instead of 128 to isolate the high-frequency watermark band before correlating, or (b) until validated against real watermarked-vs-clean samples, drop watermark from the weighted verdict (set its weight to 0 / runWatermark:false) so it cannot fabricate confidence. Note watermarkVideo is never invoked anywhere in the pipeline, so no footage actually carries a watermark — Layer 3 currently can only produce false matches, never true ones.

### [MEDIUM] Public /submit endpoint runs unbounded ffmpeg/sharp detection synchronously on a 100MB attacker-controlled upload — no auth, no rate limit, no queue
**improvement** | src/routes/guard.js:99-152 (submit handler); server.js:365 (public whitelist)
POST /api/guard/:slug/submit is whitelisted public (server.js:365) and accepts up to 100MB video, then synchronously awaits detectInVideo() which spawns ffmpeg/ffprobe and sharp, decodes frames, and loops every stored fingerprint. compareByPHash is O(queryFrames x storedFrames) nested Hamming loops in JS; on a populated vault this is heavy. There is no rate limiting, no per-IP throttle, no background queue, and no auth. A handful of large uploads to the public URL can pin CPU and block the event loop / starve the Express worker that also serves Jason's authenticated app. Given uploads/guard/ shows zero legitimate traffic, the realistic 'threat' this tool currently faces is abuse of the endpoint itself, not content theft.
**Fix:** Move detection off the request path: insert the report immediately, return report_id, and run detectInVideo in the frame-analysis-queue/background, updating the row when done (the inbox already polls). Add express-rate-limit to the public guard router and consider lowering the 100MB cap. This also fixes the UX: fans get an instant ack instead of waiting on a multi-second ffmpeg run.

### [MEDIUM] DMCA generator and submit handler disagree on match_confidence scale (0-100 vs 0-1) — DMCA notices will state wrong percentages
**bug** | src/routes/markr.js:340-342 vs src/markr/detect.js:291; stored via src/routes/guard.js:138 -> db.insertGuardReport
insertGuardReport stores match_confidence = detection.overall_confidence, which detect.js produces on a 0-100 scale (Math.round(Math.min(100, combined))). But generate-dmca/:reportId does `const pct = Math.round(report.match_confidence * 100)` (markr.js:341), assuming a 0-1 scale. A real 85% detection is stored as 85 and rendered into the legal DMCA notice as '8500%'. Since the DMCA notice is the one user-facing artifact that goes to a platform's legal team, a nonsensical confidence figure undermines the filing. The two code paths were written against different scale assumptions and never reconciled.
**Fix:** Pick one scale. Since overall_confidence is 0-100 everywhere in detect.js, change the DMCA builder to treat match_confidence as already a percentage: `const pct = Math.round(report.match_confidence)`. Audit any UI (guardr-inbox.html) reading match_confidence for the same x100 assumption.

### [LOW] Two near-identical detection entry points (markr /check route and guard /submit) and an unused download path add surface without earning it
**simplification** | src/markr/detect.js:49-66 (unused downloadToTmp); src/routes/guard.js:117-126 (only file path runs detection)
detectInVideo is reachable via POST /api/markr/check (authed, takes a path) and inline in guard /submit (public, takes an upload). downloadToTmp in detect.js (lines 49-66) supports fetching a submitted URL for detection but is never called — guard /submit only runs detection on uploaded files, never on submitted_url, so URL-only reports (the common fan case: 'here's the TikTok link') get verdict 'none' with no detection attempted at all. So the most natural fan submission (a link) bypasses the entire engine, and the dead URL-download code implies a capability that isn't wired up.
**Fix:** Either wire submitted_url through downloadToTmp -> detectInVideo (with the same background-queue + rate-limit treatment from GUARD-3, since downloading arbitrary attacker URLs server-side is its own SSRF risk and needs care), or remove the dead download helper and be explicit in the UI that URL-only reports are logged for manual review, not auto-detected. Right now the gap is silent: a link-only report looks identically 'processed' to a real match.

### [LOW] Counter blends 'filed/resolved/confirmed' as 'violations' shown publicly — risk of inflated or stale community-facing numbers with zero validation
**improvement** | src/routes/guard.js:108-131; db.getGuardReportStats src/db.js:6059-6069
GET /:slug/info and /:slug/counter expose a public 'violations' number = confirmed + filed + resolved guard_reports, rendered in a community widget. Because any fan submission with report_type defaulting to 'direct_repost' becomes a report, and confirmed/filed are manual statuses Jason sets, the public counter can be moved by noise (duplicate reports, mistaken submissions, legit stitches mis-filed) and there is no dedup on submitted_url. For a creator whose brand is straight-talking honesty, a public 'violations caught' counter that can be gamed or inflated is a reputational liability more than a protection. Given current real usage is zero, this is latent, but worth gating before the public guard.kre8r.app page is promoted.
**Fix:** Dedup reports by normalized submitted_url before counting, count only 'resolved' (actually-actioned) takedowns toward the public 'violations' number, and keep 'reports received' separate. Confirm the public counter reflects verified outcomes, not raw inbound volume, so it cannot be inflated by spam to the open endpoint.
