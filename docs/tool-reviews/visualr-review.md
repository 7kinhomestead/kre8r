# VisualΩr — Synthesis

**What it is:** a quarterly "visual intelligence" pass that runs Claude Vision over channel footage/analytics, has Opus synthesize a 90-day governing profile, then injects that profile into WritΩr, BrollΩr, EditΩr Room, and VectΩr. Six findings; two structural, four polish.

## Top 3 (in priority order)

**1. VISUALR-002 (high, inter-tool) — VisualΩr ignores VAULT-001 and re-pays for Vision it already ran.**
This is the finding that directly answers your question. VAULT-001 made frame analysis persist (`footage.visual_description` + `visual_analyzed_at` cursor), but VisualΩr's local-footage path re-extracts frames with ffmpeg and re-calls Vision from scratch — `grep visual_description` in visualr.js returns **zero matches** (verified). You now have two visual-analysis systems billing the same proxy files with incompatible schemas. Fix: for `visual_analyzed_at IS NOT NULL`, hydrate from `visual_description` and only fall back to live extraction when null (scope to footage_ids; YouTube-URL path still needs live). This is the single biggest cost/speed lever.

**2. VISUALR-001 (high, bug) — VisualΩr output never reaches the EditΩr Room.** Verified live: write side double-stringifies (`setKv('...', JSON.stringify(profile))` at visualr.js:286/292, but `setKv` already stringifies — db.js:4138). Every other reader compensates with a second `JSON.parse` (writr:476/987, brollr:157/338, vectr:304, visualr status:71/profile:88 — all confirmed). editr-room.js:75 is the **one** site that dropped the parse based on a comment that got the diagnosis backwards. Result: `vis` is the inner string, the `writr_injection || contrast_finding` guard fails, and the EditΩr Room block is empty. Cleanest fix: stop double-stringifying on write, drop the compensating parse in all 6 readers — pick one convention and make every site agree. Minimal fix: restore the parse at editr-room.js:75 and delete the misleading comment.

**3. VISUALR-003 (medium, workflow) — the 90-day profile silently rots.** The prompt literally claims it "governs shoot decisions for the next 90 days," `/status` already computes `profile_age_days` (verified 75-77), and no cron exists anywhere (confirmed — server.js only mounts the route). A 200-day-old profile keeps injecting into four tools with full confidence and zero warning, exactly on the MirrΩr analytics days when Jason would act on it. ~10 lines: add `stale: profile_age_days > 90` to `/status`, render an amber "re-run for current quarter" banner. This is the Secondary Directive case — a look-at-it artifact that should be an act-on-it nudge.

### [HIGH] EditΩr Room injects an empty/broken VisualΩr block — the "editr-1 fix" removed a parse that was actually required
**bug** | src/routes/editr-room.js:73-83 (vs src/routes/visualr.js:292 write + src/db.js:4130-4140)
getKv() ALREADY JSON.parses (src/db.js:4130-4133) and setKv() ALREADY JSON.stringifies (4135-4140). But VisualΩr writes the profile via db.setKv('visual_intelligence_profile', JSON.stringify(profile)) (visualr.js:292) — i.e. it double-stringifies. The stored value is therefore a JSON string-of-a-string. Every other consumer compensates by double-parsing: writr.js (JSON.parse(getKv(...)) at lines 476-478 and 987-989), brollr.js (157-159, 338-340), vectr.js (304-306), and visualr.js's own status/profile reads (71, 88). These all work by accident because the double-parse balances the double-stringify. editr-room.js:75 is the ONE outlier: a comment claims 'getKv already JSON.parses — double-parsing threw SyntaxError silently' and it calls getKv() with NO second parse. Result: `vis` is the inner JSON STRING, not an object. It is truthy so the block is entered (line 76), but `vis.writr_injection`, `vis.contrast_finding`, `vis.avoid` are all undefined on a string — so the EditΩr Room injects a bare '## VISUAL INTELLIGENCE' header with zero content. The 'fix' did the opposite of what its comment claims: VisualΩr is STILL not reaching the EditΩr Room.
**Fix:** The root cause is the redundant JSON.stringify on the write side (visualr.js:286 and :292) fighting setKv's own stringify. Cleanest fix: store objects directly — db.setKv('...profile', profile) and db.setKv('...video_results', merged) WITHOUT JSON.stringify — then update ALL readers to use getKv() result directly (drop the JSON.parse in writr/brollr/vectr/visualr status+profile). That makes editr-room.js correct as written. If you don't want to touch every reader, the minimal fix is to restore the second parse in editr-room.js:75 (const vis = JSON.parse(require('../db').getKv('visual_intelligence_profile') || 'null')) and delete the misleading comment. Either way, pick ONE convention and make all 6 sites agree.

### [HIGH] VisualΩr ignores VAULT-001 persisted frame analysis — re-runs Claude Vision on local footage from scratch, duplicating cost the batch already paid
**inter-tool** | src/routes/visualr.js (local footage branch, analyzeFramesWithVision) vs src/db.js:1527-1528 footage.visual_description
The task's premise is that VAULT-001 (Session 91) made frame analysis persist. It does: footage.visual_description now holds Claude Vision frame JSON and visual_analyzed_at is the idempotency cursor (db.js:1527-1528, 2800-2804). But VisualΩr's local-footage path (visualr.js:~205-260) takes the proxy_path, re-extracts frames with ffmpeg, and re-calls analyzeFramesWithVision() (Sonnet) completely from scratch. It never reads footage.visual_description — grep for 'visual_description' in visualr.js returns zero matches. So Kre8r now has TWO independent visual-analysis systems that burn API cost on the same proxy files and never share results: the VaultΩr batch queue (writes visual_description) and VisualΩr (re-derives everything live). For Jason's local footage this is pure duplicated spend and slower runs; worse, the two analyses use different schemas so insights can't be cross-checked.
**Fix:** For local footage where f.visual_analyzed_at IS NOT NULL, hydrate the per-frame analysis from f.visual_description instead of re-extracting frames and re-calling Vision. Map the stored frame JSON into the shape aggregateVisionResults() expects (or add a thin adapter). Only fall back to live ffmpeg+Vision extraction when visual_description is null. This is the single biggest 'is it worth running' lever: it makes the local-footage path nearly free and ties the two systems together. YouTube-URL path legitimately still needs live extraction (no DB row), so scope the change to footage_ids only.

### [MEDIUM] No staleness nudge — profile self-describes as a 90-day governing analysis but nothing reminds Jason to re-run, so it silently rots
**workflow-order** | src/routes/visualr.js:69-80 (status) + public/mirrr.html:2871-2877 (no stale state)
The synthesis prompt literally says 'This quarterly analysis governs shoot decisions and AI generation prompts for the next 90 days' (visualr.js synthesizeProfile). status returns profile_age_days (visualr.js:75-77) and the UI shows 'Profile built Xd ago' (mirrr.html:2874), but nothing ever flags the profile as STALE or expired. There is no cron/scheduler reference to VisualΩr anywhere in src (confirmed by grep). A 200-day-old profile keeps silently injecting into WritΩr/BrollΩr/EditΩr/VectΩr with full confidence and no warning. On non-filming analytics days — exactly when Jason is in MirrΩr — there is no surfaced 'your visual profile is 95 days old, re-run it' prompt. This is the SECONDARY DIRECTIVE failure mode: the tool generates a profile he looks at once, then it quietly drifts out of date while still steering every script's b-roll. It changes what he creates, but with possibly-stale rules he can't tell are stale.
**Fix:** Add a stale flag in /status (e.g. profile_age_days > 90 → stale:true) and render it in mirrr.html as an amber 'Profile is N days old — re-run for current quarter' banner on the VisualΩr card. Optionally surface the same staleness as a single line in the consuming prompts ('NOTE: visual profile is N days old') so the LLM weights it appropriately. This converts a look-at-it artifact into an act-on-it nudge for ~10 lines of code.

### [MEDIUM] retention_signal is an LLM guess from a single still frame, then surfaced as a hard percentage — risks steering shoots on noise
**improvement** | src/routes/visualr.js analyzeFramesWithVision prompt + aggregateVisionResults (strong_retention_pct/weak_retention_pct) + formatVideoBlock
In analyzeFramesWithVision the per-frame schema asks Claude Vision to label each still with retention_signal 'strong|neutral|weak' (visualr.js prompt). A model cannot infer audience retention from one isolated frame with no motion, audio, or watch-time data — it is pattern-matching on 'does this frame look engaging,' which is circular. aggregateVisionResults then converts those guesses into strong_retention_pct / weak_retention_pct (visualr.js), which formatVideoBlock renders as 'Strong retention frames: 40%' and feeds to Opus as if it were measured signal. The ACTUAL retention ground truth exists in the analytics-screenshot path (extractAnalyticsFromScreenshots reads real retention curves and drop-offs) — but that path is optional and the frame-derived pseudo-retention is always present and always labeled as 'retention'. For a creator whose CLAUDE.md explicitly documents an inverse views/retention relationship, conflating a vibe-from-a-still with real retention is exactly the wrong signal to amplify.
**Fix:** Rename the frame-level field to something honest like 'visual_engagement_guess' and label it that way in formatVideoBlock so Opus doesn't treat it as measured retention. Reserve the word 'retention' for the analytics-screenshot path, which is real. In the synthesis prompt, instruct Opus to weight screenshot-derived retention over frame-derived engagement when both exist. Cheap honesty fix that protects against acting on noise.

### [LOW] Per-frame analysis silently mis-aligns timestamps and data when Claude returns fewer frames than sent
**bug** | src/routes/visualr.js analyzeFramesWithVision (timestamp re-attach) + aggregateVisionResults (opening slices)
analyzeFramesWithVision re-attaches timestamps by index: parsed.frames.map((f,i)=>({...f, timestamp_s: frames[i]?.timestamp_s ?? f.timestamp_s})) (visualr.js). If Claude Vision returns N-1 entries for N frames (drops one, or returns them out of order despite the prompt), every subsequent frame's analysis gets stamped with the WRONG frame's timestamp, and the opening-window slices in aggregateVisionResults (opening = valid.slice(0, floor(n*0.1))) silently analyze the wrong frames. There is no length-check between frames sent and frames returned. opening_face_pct / opening_warm_score / opening_outdoor_score — which directly drive opening_frame_rules injected into WritΩr — are the most position-sensitive outputs and the most likely to be corrupted by a single dropped frame.
**Fix:** After parsing, validate parsed.frames.length === frames.length; if mismatched, either reconcile by the model-returned frame_index/timestamp_s (the prompt already requests both) rather than positional index, or drop the video with a 'warn' SSE event rather than emitting misaligned opening-frame rules. At minimum, log a warning when counts differ so a corrupted opening profile isn't injected invisibly.

Keep it terse to avoid prompt bloat, but make the highest-signal field (audience_attention_profile) reach the writer.
