# VaultΩr Architectural Review — Synthesis (4000+ clips)

## Verdict: The 2-3 things making VaultΩr feel heavy at scale

**1. The grid only ever holds 100 rows, but every filter, tag cloud, and bulk action acts on those 100 rows.** The server returns one 100-row page, then `applyFilters()` in vault.html runs orientation/platform/posted/braw/subject/organized filters *client-side against only the current page*. Filter by "needs proxy" or a subject tag and the creator sees a near-empty grid and concludes their footage is gone. Selection, bulk-assign, and the tag cloud have the identical defect. **This is the single biggest reason the tool feels cumbersome and untrustworthy** (`vault-imp-1`, `vault-imp-2`, `VAULT-IT-02`). It is not a performance problem — it is a correctness problem the creator experiences as "the vault lost my footage."

**2. The footage table has no indexes for what it actually filters/sorts, and every list query is `SELECT *` pulling KB-sized transcript + visual_description blobs into each row.** Every page load, stat-panel refresh, dedupe pass, and `getAllFootage().filter()` job does a full table scan over 4000 rows with large TEXT columns, then ships megabytes the grid never displays. Page loads and stat panels are sluggish purely because of missing indexes and missing column projection (`vault-imp-3`, `VAULT-IT-07`, `vault-imp-10`).

**3. The page leads with 7 manual ingest/maintenance panels for work the watcher already automates, and asks the creator to make cost/model/batch decisions they shouldn't.** Daily intake is fully automatic (watcher → classify → transcribe → frame-analyze), yet INGEST/UPLOAD/DRIVE-OPS/ARCHIVE/DAVINCI/FRAME-BACKFILL dominate the top of the page and the FOOTAGE LIBRARY is buried at line 806. The frame-analysis panel forces ~20 manual re-clicks plus shot-type/limit/model/cost decisions per drain. Every panel is a decision surface the non-technical creator scans past (`vault-01`, `vault-imp-4`, `vault-05`, `vault-08`).

**Plus one silent catastrophe underneath all of it:** frame analysis has never persisted a single result (VAULT-001). It's not felt as "heavy" — it's felt as endless re-running, a cost meter that never finishes, and dashboards permanently stuck at "100% pending."

### CRITICAL

**F1 — Frame analysis results are silently discarded (whitelist omits the only two columns it writes)**
`src/db.js:2793-2806` (allowed list) vs `src/vault/frame-analysis-queue.js:413-416`. **CONFIRMED by direct read.** `updateFootage`'s `allowed` array does not contain `visual_description` or `visual_analyzed_at`; the queue writes *only* those two keys, so `updates.length === 0` and line 2802 returns writing nothing. Every live-Opus and batch-Haiku analysis burns API cost, marks the job done, broadcasts `frame_done`, and persists nothing. Because `visual_analyzed_at` stays NULL forever, the batch cursor (`WHERE visual_analyzed_at IS NULL`) re-selects the same 4000 clips on every run — infinite re-analysis, runaway cost. **Blast radius (was VAULT-014):** AssemblΩr Call 2 and VisualΩr run with no visual signal; MirrΩr/Mission dashboards show 100% pending forever, driving endless re-runs.
**Fix:** Add `'visual_description'` and `'visual_analyzed_at'` to the `allowed` array (db.js:2794-2800). Make `updateFootage` log when handed keys outside the whitelist so the next silent-drop surfaces. Verify a manual run sets `visual_analyzed_at` non-NULL, then confirm AssemblΩr Call 2 receives data and the MirrΩr pending count drops.

**F2 — Client-side filters/tag-cloud/selection only see the current 100-row page**
`public/vault.html:1207-1238` (loadFootage), `:1284-1309` (applyFilters), `:1361-1399` (renderTagCloud); `src/routes/vault.js` GET /footage; `src/db.js:2839`. Server filters only on shot_type + quality_flag; everything else filters client-side over the 100 loaded rows. Creator filtering by "needs proxy"/subject tag/"unposted" sees a near-empty grid and believes footage is lost (Prime Directive violation). Tag cloud aggregates only the current page, so its ~35 tags are a random slice.
**Fix:** Push ALL filters server-side (extend `getAllFootage`/`countFootage` for orientation, braw state, posted/unposted via EXISTS on clip_distribution, subject LIKE, organized state); paginate the filtered set and return count + rows. Tag cloud from a dedicated whole-vault aggregate endpoint.

### [CRITICAL] Frame analysis results are silently discarded — updateFootage whitelist omits visual_description/visual_analyzed_at
**Dimension:** bug | **Location:** src/db.js:2793-2806 (allowed list) vs src/vault/frame-analysis-queue.js:413-416
**Problem:** frame-analysis-queue.js processNext() persists results with db.updateFootage(job.footage_id, { visual_description: JSON.stringify(result), visual_analyzed_at: new Date().toISOString() }) (frame-analysis-queue.js:413-416). But db.updateFootage()'s `allowed` whitelist (db.js:2794-2800) does NOT include 'visual_description' or 'visual_analyzed_at'. Object.keys(fields).filter(k => allowed.includes(k)) strips both fields, leaving updates.length === 0, so the function returns early at db.js:2802 and writes NOTHING. Every frame analysis (live Opus AND batch Haiku) burns API cost, marks the job 'done', broadcasts frame_done, but the DB row is never updated. Because visual_analyzed_at stays NULL forever, the idempotency cursor (getUnanalyzedFootage WHERE visual_analyzed_at IS NULL) re-selects the SAME clips on every batch run — at 4000 clips this means infinite re-analysis, runaway cost, and AssemblΩr never sees any visual_description. This is the single most damaging bug in VaultΩr: the entire frame-analysis subsystem is a no-op at the persistence layer.
**Fix:** Add 'visual_description' and 'visual_analyzed_at' to the `allowed` array in updateFootage (db.js:2794-2800). Verify with a manual frame-queue run that footage.visual_analyzed_at becomes non-NULL. Consider making updateFootage throw or log when it receives keys not in the whitelist, so future silent-drop bugs surface immediately instead of failing quietly.

### [HIGH] Watcher race: rapid file arrival can ingest the same clip twice (no in-flight dedup)
**Dimension:** bug | **Location:** src/vault/watcher.js:168-231; guard at src/vault/intake.js:436-438
**Problem:** The watcher 'add' handler (watcher.js:168-231) calls ingestFile immediately and concurrently for every event — there is no per-path in-flight lock. processFile's only dedup guard is db.footageFilePathExists() (intake.js:436), checked at the START of processing. For a single clip, ffprobe + 3 thumbnails + a Vision API call take many seconds. If chokidar emits two events for the same path close together (common on Windows network/SMB drives, or DaVinci rewriting a proxy in place, or a stop/start of the watcher), both calls pass the existence check before either inserts, and the clip is ingested twice. The same window exists between the watcher and a manual /ingest or /upload of the same file. At 4000+ clips arriving in bursts from a batch proxy export, duplicate inserts accumulate — exactly the 'cumbersome at scale' symptom. dedupeFootage exists as a cleanup, but the Prime Directive favors not creating the mess.
**Fix:** Maintain an in-memory Set of in-flight absolute paths in intake.js (or watcher.js); add the path before processing and remove it in a finally block, rejecting/short-circuiting if already in-flight. Alternatively add a UNIQUE index on footage(file_path) and treat the constraint violation as 'skipped'. A DB-level unique constraint is the durable fix since it also covers the watcher-vs-upload race.
