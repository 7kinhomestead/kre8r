# TeleprΩmpter Review — Synthesised

Three independent review passes produced 33 raw findings. After deduplication (multiple reviewers flagged the same in-memory script store, the same `writr_complete` gate, the same `getLocalIP`/QR issues, the same beat-map disconnect), the consolidated set is **23 distinct findings**.

---

## TOP 3 BY CREATOR IMPACT

1. **Wake lock dies mid-take (CRITICAL).** The phone screen sleeps during a monologue and the prompter goes black — the exact "worst-possible-moment" failure the Prime Directive warns about. Wake lock is requested once and never re-acquired after the screen blanks; the LAN/laptop path requests none at all. Fix: a `visibilitychange` re-acquire helper called from every display mode.

2. **Secondary screen snaps to top of script on any WiFi blip (CRITICAL).** Outdoors, a WebSocket drop triggers a reconnect that unconditionally resets `scrollTop = 0`, throwing the talent back to the start of the script mid-take with no recovery. Fix: a `firstRegister` flag so reconnects re-sync via the next `state` message instead of resetting.

3. **Pre-shoot pairing is fragile and silently joins stale sessions (HIGH cluster).** Three reinforcing failures land Jason in the field debugging why devices won't pair: QRs render before a session code exists and fall back to a *previous* shoot's localStorage code (TP-1); a display reconnecting with a dead code silently spawns a phantom empty session while Cari's remote controls nothing (TP-2); and `getLocalIP` can encode an unreachable interface into the QR (TP-03/TP-11). Fix: don't render pairing QRs until a live session code exists, never auto-reuse stale localStorage codes, and prefer the gateway/request-matched interface.

## THE BACK-BUTTON ISSUE (Known Issue #7) — RESOLVED DIAGNOSIS

The known issue is **partially stale and partially real**:

- **STALE for the display screen.** The display already has three exits: a persistent ✕ (`tp-exit-btn`), the Escape key, and "📋 Scripts" / "✕ Exit" in the controls bar. CLAUDE.md issue #7 ("no back button from display screen") should be **closed**. Residual polish: the labeled controls bar auto-hides after 3s and the persistent ✕ is a small low-contrast glyph — hard to see on a phone in bright sun. Make it larger/higher-contrast on touch and flash a one-time "Tap ✕ or Esc to exit" hint.

- **STILL REAL for the phone-facing screens.** The actual field dead-end is on **#tp-remote, #tp-voice-device, and #tp-join** — none have an escape route. Once a phone scans the control/voice QR, the URL carries `?mode=control|voice` and `init()` routes `P_MODE` straight back on reload. Wrong role or wrong session = stuck retyping a URL on a phone. **Fix:** add a fixed back button to those three screens that closes the WS, clears the localStorage session codes, and strips the URL params via `history.replaceState('/teleprompter.html')` before showing the selector — without clearing the params, `init()` re-routes back into the same mode.

Net: reframe #7 from "display has no back button" (false) to "control/voice/join phone screens have no exit and field-load failures dead-end to a laptop-only setup screen."

## CROSS-CUTTING THEMES
- **In-memory state vs. the Prime Directive** — both `fieldScripts` and WS `sessions` are RAM-only; a restart mid-shoot is unrecoverable in the field. Persist field scripts (SQLite/kv_store) + phone-side localStorage cache.
- **Silent failure at the worst moment** — wrong-IP QRs, dead cloud endpoint, blank secondary display, missing approved script, stale-code phantom sessions all fail *quietly* exactly when Jason is in the field. Add positive confirmation (Ready state, heartbeat, reachability round-trip) over silent best-effort.
- **One-tap-to-start convergence** — wake lock, fullscreen, and AudioContext all need a user gesture; a single "Tap to start" on auto-start paths fixes TP-01, TP-09, and the voice-gesture requirement together.
- **Single source of truth for beats** — TeleprΩmpter parsing inline markers while ShootDay reads `beat_map_json` is a data-model split that should be resolved before any cross-tool coverage work.

## Full Findings (30 total)
### [CRITICAL] Secondary display jumps to top of script on any WiFi blip mid-take
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\teleprompter.html:2406 (inside connectSecondaryDisplayWS registered handler) and reconnect onclose ~2470+
**Problem:** When a follower (secondary) display's WebSocket drops outdoors (WiFi blip — common in the field), connectSecondaryDisplayWS()'s onclose fires _connect() again. On reconnect the server replies 'registered', and the registered handler unconditionally runs `document.getElementById('tp-scroll-wrap').scrollTop = 0` and re-fetches the script. So the second teleprompter screen (tablet/laptop) snaps back to the START of the script in the middle of a take. The talent reading that screen loses their place with no recovery. The primary display does NOT have this bug because its 'registered' handler does not reset scrollTop. This directly violates the prime directive (never break the creative thread).
**Fix:** Only reset scrollTop to 0 on the FIRST registration, not on reconnect. Track a `firstRegister` flag (set false after initial render). On reconnect, skip the scrollTop=0 and the re-render/re-fetch; rely on the next incoming `state` message to re-sync position. The follower already receives position via state sync, so it will catch up gracefully instead of snapping to top.

### [HIGH] Control device registering with stale code silently creates a phantom session instead of erroring
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\routes\teleprompter.js — register handler, isDisplay branch (`const joining = ...` / `const sessionCode = ...`)
**Problem:** In the WS register handler for role 'display', the join logic is: `const joining = code && code.length===4 && sessions.has(code); const sessionCode = joining ? code : (code && code.length===4 ? code : generateCode());`. If a display reconnects (or a QR is reused after the session was cleaned up) with a 4-digit code that no longer exists, it does NOT error — it CREATES a brand new empty session reusing that code. Meanwhile control devices that registered against the original session are now orphaned in a different session object (or the cleanup timer deleted theirs). Result: the operator's remote (Cari) silently controls nothing while the talent thinks they're synced. There is no 'session not found' feedback for displays, unlike controls.
**Fix:** Collapse the ternary: a display that passes a 4-digit code should JOIN only if the session exists; if it passed a code that doesn't exist, generate a fresh code AND notify the client of the new code so QR/UI updates. The client already handles the 'registered' session field, so just always `sessionCode = joining ? code : generateCode()` and never reuse a non-existent client code as-is.

### [HIGH] No back/exit button on Remote, Voice, and Join screens — field dead-ends (known issue #7)
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\teleprompter.html — #tp-remote (~1032), #tp-voice-device (~1131), #tp-join (~1099): none contain a backToSelector/home control
**Problem:** The display screen now has #tp-exit-btn and a '📋 Scripts' button, but the three phone-facing screens have NO escape route: #tp-remote (control), #tp-voice-device (voice), and #tp-join (choice) render no back button. **Fix:** Add a small fixed back button to #tp-remote, #tp-voice-device, and #tp-join that calls a reset (close WS, clear localStorage session codes, strip URL params via history.replaceState to '/teleprompter.html', show selector). ### [HIGH] Field-mode load failure strands the phone with no auto-retry
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\teleprompter.html:1530-1540 (loadFieldScript catch block)
**Problem:** loadFieldScript() on a failed fetch (expired code, cell-data hiccup) shows the error and, after 2s, appends a '← Back to Setup' button that navigates to /teleprompter.html with NO field param — i.e. back to the laptop-oriented selector, useless on a phone with cell data only. There is no retry of the same code. In the field this means a transient network error on script fetch forces regenerating a whole new QR from the laptop. Worse: the catch appends a new button every time it's reached, and there's no guard, so repeated triggers could stack buttons.
**Fix:** On field fetch failure, offer a 'Retry' button that re-calls loadFieldScript(code) with the same code, plus distinguish 404/expired (regenerate QR) from network error (retry). Guard against appending duplicate buttons (check if one already exists).

### [MEDIUM] fieldScripts and sessions are pure in-memory Maps — server restart mid-shoot loses everything
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\routes\teleprompter.js — `const fieldScripts = new Map()` and `const sessions = new Map()`
**Problem:** Both the field-script store (`fieldScripts`) and WS `sessions` are in-memory only. If the Node/Electron process restarts during a shoot (crash, Electron auto-backup hiccup, OOM), every field code 404s and every WS session is gone. Field codes have a 24h TTL but no persistence, so a restart silently invalidates the QR a phone is holding. Given the prime directive (never lose creative state in the field) and that this is the moment of shooting, there is no recovery path server-side. The client has localStorage recovery for the DISPLAY, but a phone holding a field code gets a hard 404.
**Fix:** Persist field scripts to a lightweight on-disk store (or the SQLite kv_store, consistent with the TikTok PKCE pattern noted in CLAUDE.md) keyed by code with TTL, and rehydrate on boot. At minimum, make the field-script 404 message instruct re-launch rather than implying the code was wrong.

### [MEDIUM] End-of-script in voice mode can resume scrolling past the end due to pending silence timers
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\teleprompter.html:1947-1951 (animTick end-of-script) interacting with sampleVoiceVolume ~ and silenceTimer logic
**Problem:** In animTick(), when scroll reaches the end in voice mode it sets `voiceEffectiveSpd=0; voiceScrolling=false`. But sampleVoiceVolume() runs every frame and, on the next loud sample, sets voiceScrolling=true and recomputes voiceEffectiveSpd > 0 again, while a previously-scheduled silenceTimer (set before end-of-script) may still fire and stomp state. The combination can cause the scroll to keep nudging / flip state at the very end of the script, and the end-stop only triggers within 8px of the bottom, so a louder delivery re-engages scroll attempts at EOF. Not a crash but causes jitter/false motion at the most important moment (the closing line).
**Fix:** Add an explicit `atEnd` latch set when EOF is reached; in sampleVoiceVolume, do not re-engage scrolling while atEnd is true and scrollTop is still at the bottom. Clear the latch only when the user seeks/restarts.

### [MEDIUM] _lastBroadcastBeat not reset on script reload / speaker-filter change — beat pills desync
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\teleprompter.html:2023-2030 (_lastBroadcastBeat) and renderScript/setSpeakerFilter call sites

### [MEDIUM] Empty-session cleanup timer keys on stale myCode and can delete a freshly-reused session
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\routes\teleprompter.js — ws.on('close') cleanup setTimeout block
**Problem:** On WS close, if a session is empty, a 30-min setTimeout deletes sessions.get(myCode) if still empty. But `myCode` is captured per-connection. ### [CRITICAL] Wake lock never re-acquired after screen blanks — display dies mid-take outdoors
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\public\teleprompter.html:1916-1918 (startSoloMode), 3201-3203 (voice device); startTeleprompter() at 1857 has no wake lock request
**Problem:** The screen Wake Lock is requested exactly once (line 1916 startSoloMode, 3201 voice device) and never re-acquired. The Wake Lock API auto-releases the moment the page loses visibility — phone auto-lock, a pulled-down notification shade, switching apps to check a text, or even some browsers dimming after inactivity. Once released it stays released; there is no `visibilitychange` listener to re-request it. For an outdoor shoot this is the worst-possible-moment failure the Prime Directive warns about: Jason is mid-monologue, the phone screen sleeps, the prompter goes black, and the take is dead. Also the laptop/LAN display path (startTeleprompter) requests NO wake lock at all — only solo and voice-device modes do.
**Fix:** Add a single re-acquire helper and a visibilitychange listener: on `document.visibilityState === 'visible'` re-request `navigator.wakeLock.request('screen')` if the previous lock released. Store the lock object and listen for its `release` event. Call the helper from startTeleprompter() too (every display mode, not just solo), so the laptop/tablet rig also stays awake. This is the single highest-value reliability fix in the tool.

### [HIGH] Field/cloud scripts live only in server RAM — a server restart loses the script mid-shoot
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\routes\teleprompter.js — fieldScripts Map (~line with `const fieldScripts = new Map()`), GET /field-script/:code
**Problem:** Field-mode scripts are stored in an in-memory `Map` (fieldScripts) with a 24h TTL. On the DigitalOcean cloud path this is the ONLY copy the phone can reach. If pm2 restarts the process (deploy, crash, OOM) between generating the QR and the phone fetching — or if the phone needs to re-fetch after a reconnect — the script is gone and returns 404 'Generate a new QR from the laptop.' In the field, away from the laptop, that recovery instruction is impossible to follow: Jason may not have the laptop open, and the laptop may be on a different network. There is no persistence and no fallback copy on the phone.
**Fix:** Once the phone fetches a field script, cache the full text in the phone's localStorage (keyed by code) so a re-fetch/reconnect survives a server blip. On the server, optionally persist fieldScripts to a small SQLite table or disk file so a restart doesn't wipe active codes. At minimum, make the 404 message actionable offline (e.g. 'Script expired — re-open the last script from this phone' if a localStorage copy exists).
