### [HIGH] Stream can end without a terminal 'done' event, leaving the UI cursor blinking forever
**Dimension:** bug | **Location:** src/routes/lab.js:180-200 (trailing buffer discarded), 193 (done only on message_stop)
**Problem:** The server only sends `{type:'done'}` when it parses an Anthropic `message_stop` event (lab.js:193). If the upstream stream closes after the final content_block_delta but the message_stop line lands in the trailing `buffer` (it is never flushed — the final `buffer = lines.pop()` remainder is discarded after the for-await loop at lab.js:198, only `res.end()` is called), no 'done' is emitted. On the frontend, the cursor is only removed on `evt.type==='done'` or on natural reader completion. The natural-completion path (`if (done) break`) does remove the cursor afterward at the finalize step (sendMessage finally block), so the visible cursor is eventually cleaned — BUT the assistant message is only pushed to state.messages/persisted if `assistantText` is truthy, and a 'done' was never required. The deeper issue: the discarded trailing buffer means a final partial SSE line from Anthropic (a token delta not terminated by \n) is dropped, truncating the last token(s) of the answer.
**Fix:** After the for-await loop, flush the decoder and process any remaining `buffer` content before res.end(). Always emit `send({type:'done'})` before res.end() regardless of whether message_stop was seen, so the client has a deterministic terminator.

### [HIGH] Frontend SSE parser uses slice(5) while server emits 'data: ' with a space — works by luck via trim(), but error events with leading-bracket payloads can break
**Dimension:** bug | **Location:** src/routes/lab.js:186-187 (slice(6) assumes 'data: ' with space)
**Problem:** Server writes `data: <json>\n\n` (lab.js:84, note the space after colon). Frontend filters on `line.startsWith('data:')` then does `line.slice(5).trim()` (frontend sendMessage). slice(5) keeps the leading space, then trim() removes it, so it currently works. However the server's OWN upstream parser (lab.js:186-187) requires `line.startsWith('data: ')` WITH the space and uses slice(6). Anthropic's SSE actually emits `data: ` with a space so that is fine, but this asymmetry (one parser assumes space, other strips it) is fragile. The real latent bug: if Anthropic ever emits `data:<json>` without the space (spec-legal), the server's slice(6) would corrupt the JSON and silently swallow it in the catch, dropping tokens with zero error surfaced.
**Fix:** Make the server tolerant: `if (!line.startsWith('data:')) continue; const raw = line.slice(line.indexOf(':')+1).trim();` so both spaced and unspaced SSE framing parse correctly.

**Problem:** db.getApprovedWritrScript runs _parseWritrScript which JSON.parses beat_map_json into an object/array before returning (db.js:4014). ### [MEDIUM] No abort/cancel — navigating or sending again mid-stream orphans the fetch and the server keeps writing to a dead socket
**Dimension:** bug | **Location:** src/routes/lab.js:78-200 (no req.on('close'), no upstream abort); frontend sendMessage (no AbortController)
**Problem:** sendMessage holds an open SSE fetch with no AbortController. setStreaming(true) disables input so a second send is blocked, but if the user navigates away (Electron nav) or closes the tab mid-stream, the client reader is abandoned while the server's for-await over claudeRes.body keeps running and calling send() (lab.js:84 guards on res.writableEnded, which becomes true only after the socket errors). There is also no `req.on('close')` handler to abort the upstream Anthropic fetch, so a cancelled chat keeps consuming Anthropic tokens (cost) until the model finishes. The assistant text generated after the user leaves is never persisted — work in flight is lost with no recovery.
**Fix:** On the server, create an AbortController, pass signal to the node-fetch call, and `req.on('close', () => controller.abort())`. On the client, store the AbortController on state and abort it in newChat()/on unload so partial state is cleanly handled.
