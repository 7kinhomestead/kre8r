# EditΩr Room — Review Synthesis

## Verdict on workflow position: KEEP it, but as the "assembly critic," not a third generic chat

EditΩr Room earns its place — but only on one defensible claim. With WritΩr Room (pre-production, knows the draft script, can write an approved revision back) and LabΩr (open-ended "ask anything," knows footage inventory with visual analysis, but stateless) both existing, the three surfaces collide on nearly everything: same "direct, not cheerleader" persona, same beat-map + script + voice + VisualΩr context, same pitch of "pacing / story structure / b-roll / which take is stronger."

**The one thing only EditΩr Room can structurally know is the per-beat ASSEMBLY STATE** — `selected_takes` count, `takes` count, `assembly_note`, and (when wired) `coverage_confidence` + `critique_note` from AssemblΩr's Call-2. That is what lets it say "you put the fumbled take right before the payoff" or "beat 4's strong take is buried." Neither other surface can answer that. **And it is the only Room that feeds another module** — BrollΩr inherits its conversation to make b-roll story-aware. That downstream wire is its strongest justification to exist.

So: do **not** merge EditΩr Room into the others. Instead consolidate the *plumbing* (3 SSE handlers, 3 session stores, 3 hand-rolled prompt builders, copy-pasted VisualΩr injection) onto one shared room engine parameterized by stage (`write` / `edit` / `open`), and narrow each surface to a one-sentence identity:
- **WritΩr Room** = script revision (writes scripts back)
- **EditΩr Room** = assembly critique (feeds BrollΩr)
- **LabΩr** = canonical "ask anything" (full page, footage context)

The creator's "role is unclear" complaint is the direct symptom of the overlap, not a missing feature.

## Top 3 by creator impact

### 1. VisualΩr context silently never loads (HIGH, verified)
`buildSystemPrompt` does `JSON.parse(getKv('visual_intelligence_profile'))` at `src/routes/editr-room.js:75`, but `getKv` (db.js:4132) already returns parsed JSON. `JSON.parse(object)` throws, the surrounding `try/catch(_){}` (lines 72–83) swallows it, and the entire visual-intelligence block (`contrast_finding`, `writr_injection`, avoid-patterns) is never injected. The Room's prompt claims "you know everything about this edit" while silently missing the channel-performance intelligence. brollr.js:107 uses `getKv` correctly, confirming this route is the bug. **Fix:** delete the redundant `JSON.parse` — use the object directly. One-line fix, restores a whole context channel.

### 2. EditΩr Room reasons about the cut blind to AssemblΩr's own confidence + self-critique (HIGH, verified)
The Room's stated job is to flag buried strong takes and weakly-covered beats. AssemblΩr already computes exactly that — `coverage_confidence` and `critique_note` per beat — and `getSelectsByProject` returns them (db.js:3819–3823). But `buildSystemPrompt` (editr-room.js:42–49) reads only `assembly_note` and take counts; the two richest signals are loaded into the row and dropped. The surface's one differentiated job is starved of the one data it uniquely has access to. **Fix:** append `coverage_confidence`/`critique_note` (and optionally `beat_brief`) in the beatBlock loop — no new query needed.

### 3. The Room talks but never acts — creative state lives only as chat prose (HIGH, creator-facing)
EditΩr Room writes nothing back to the edit. A decision like "beat 4 should lead with take 2, beat 6 needs b-roll" exists only as kv_store chat text the creator must manually re-execute in AssemblΩr — and BrollΩr must re-infer intent from raw prose. This both *adds* a decision (remember + re-apply) and risks losing creative state (a "Clear session" wipes it with no archive; the user's message is also lost on stream error — editr-room.js handler never server-saves, only the client POSTs on `done`). Contrast WritΩr Room's `/room/approve` which crystallizes a decision into a durable record. This is the core reason the Room "talks but doesn't help." **Fix:** add a minimal write-back (pin a suggestion to a beat → updates `assembly_note` / new `editor_decision` field), server-persist the turn inside `/chat`, and archive on clear. Directly serves both the Prime and Secondary directives.

### [MEDIUM] timeoutMs option is silently ignored — chat can hang forever
**Dimension:** bug | **Location:** src/routes/editr-room.js:162 + src/utils/claude.js:282-286
**Problem:** The /chat route passes { tool: 'editr-room', timeoutMs: 60_000 } as the options arg to callClaudeStream (line 162), clearly intending a 60s upstream timeout. But callClaudeStream only destructures `const { tool = 'fence', session_id = null } = options` (src/utils/claude.js:286) and never reads timeoutMs. There is no AbortController/timeout anywhere in callClaudeStream — it awaits a Promise that only resolves on stream 'end' or rejects on 'error'. If the Anthropic stream stalls without erroring, the await never resolves, the 20s SSE heartbeat keeps writing ': keepalive' forever, and the request hangs indefinitely with no upstream cap. The author's intended safety net does nothing.
**Fix:** Either implement timeoutMs in callClaudeStream (wrap the fetch + stream Promise in an AbortController that aborts after options.timeoutMs and rejects), or add a client-side timeout in the route. Minimum: honor timeoutMs in claude.js so all callers (not just EditΩr Room) get the cap.

### [MEDIUM] Creator's message lost on stream error — session never saved
**Dimension:** bug | **Location:** public/editor.html:1920 + 1959-1968 + 1969-1979
**Problem:** In sendEditrRoomMsg, the user's message is pushed to editrRoomMessages immediately (editor.html:1920) and rendered, but the session is only POSTed to the server inside the evt.type==='done' branch (line 1963-1967).
