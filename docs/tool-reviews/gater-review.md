## GateΩr Review — Synthesis

GateΩr is the M1 distribution-entry gate: the creator's single approval queue that walks a picture-locked video through package → captions → emails before it ships. The review surfaced 7 findings. The pattern across all of them: the gate *works* mechanically (SQL is idempotent, no corruption risk), but it's leaking pre-production noise in, has no way out, and speaks two dialects at once.

### Top 3 by creator impact

**1. The queue shows pre-production projects (gate-1, high).** This is the headline. `/api/projects` with no source param returns every non-archived native project — so brand-new SeedΩr ideas and un-shot WritΩr/ShootDay projects render as "NOT STARTED" cards in the approval queue, burying the 2-3 videos actually awaiting a decision. This is a direct hit on the Secondary Directive: the creator opens the gate to *reduce* decisions and instead gets shown work that has no business being gated. The fix is cheap because the signal already exists — `current_stage` starting with "M" (the auto-advance trigger at vault.js:195-211 already sets it). Filter on it. This is the one to fix first.

**2. No reject / send-back path (gate-4, medium — but punches above its severity).** Every gate offers only Approve or Regenerate. If the creator looks at the picture-locked video and decides the *edit* is wrong, GateΩr has no affordance to kick it back to ComposΩr/EditΩr — they must leave the dashboard and hunt for the prior stage manually. This violates the Prime Directive head-on: "if this goes wrong, how do they get it back?" At M1 — the very first distribution decision — the answer is currently "navigate away and figure it out." A one-way ratchet on the most consequential gate is the riskiest design gap here, severity rating notwithstanding.

**3. Approve is not double-click-guarded and full-reloads the queue (gate-3, medium).** Buttons aren't disabled in-flight, so a double-tap on the touch workflow fires two POSTs. No corruption (idempotent SQL), but `selectPackage` with a different package between taps silently re-locks a different selection. Worse for feel: every approval does `setTimeout(loadDashboard, 1200)` — a full refetch that reflows the queue and loses scroll position, so a fast approval can feel like it "didn't take." Disable-on-click plus advance-the-single-block-in-place fixes both the race and the jarring reflow.

### Does it earn its place as a gate, or is it friction?

**It earns its place — but it's currently importing its own friction.** The *concept* is correct and directive-aligned: a single deliberate checkpoint between "edited" and "public" is exactly the kind of decision-consolidation the system should have, and the creator genuinely wants one human yes/no before content ships. The problem is purely in the implementation hygiene, and it splits cleanly:

- **Real friction to remove now:** the pre-production leak (gate-1) and the missing recovery path (gate-4). The first makes the gate noisy enough to ignore; the second makes it unsafe to trust. Together they're what would make a creator stop using it.
- **Polish, not friction:** the double-click/reflow race (gate-3) and the A/B/C-vs-M1-M5 naming collision (gate-6) — the latter is a genuine cognitive tax (one screen says "GateΩr M1" but contains "Gate A" that advances to "M3"), worth fixing but not load-bearing.
- **Code-health, invisible to creator:** the gridHtml attribute-splicing hack (gate-5), the partial-write-vs-not-generated detection gap (gate-2), and the 3x-duplicated header markup (gate-7). These are drift/maintenance risks; gate-7's duplication is what would make gate-6's relabel fan out to ~7 edit sites, so fix gate-7 *before* gate-6.

**Verdict:** Keep the gate. Fix gate-1 and gate-4 first — those two are the difference between a gate the creator relies on and a queue they learn to scroll past. Everything else is cleanup that can ride a later pass.

**Suggested order:** gate-1 (filter the queue) → gate-4 (add send-back) → gate-3 (guard + in-place advance) → gate-7 then gate-6 (dedupe header, then relabel once) → gate-5, gate-2.

## Findings (7 total)
### [HIGH] GateΩr queue shows pre-production projects, multiplying decisions instead of reducing them
**improvement** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html (renderDashboard, awaitingGen filter) + C:\Users\18054\kre8r\src\db.js:4114 getPipelineSummary
The dashboard calls /api/projects with no ?source param → db.getPipelineSummary(null) → getKre8rProjects(), which returns EVERY non-archived native project regardless of pipeline stage (src/db.js:2545-2562, WHERE only filters archived + import sources). A brand-new SeedΩr idea or a project still in WritΩr/ShootDay (package_count=0, no gates) lands in GateΩr's awaitingGen block rendered as a 'NOT STARTED' card urging '→ Generate Packages in PackageΩr', and again in 'ALL PROJECTS' as 'New'. GateΩr is M1 (picture-lock / distribution entry); a project that hasn't been shot or edited should never appear here. This directly violates the Secondary Directive ('does this reduce decisions or add one?') — the creator on a non-filming day opens the approval queue and is shown pre-production work that has no business being gated, burying the 2-3 videos actually awaiting a decision. The auto-advance-to-M1 trigger exists (vault.js:195-211 on completed-video), so the dashboard already has a real signal (current_stage starting 'M1'+) it could filter on but doesn't.
**Fix:** Filter the queue to projects that have actually reached distribution. Either (a) in renderDashboard only push to awaitingGen when the project's current_stage starts with 'M' (reached picture-lock), dropping pre-production projects entirely, or (b) add a server-side filter — e.g. /api/projects?stage=distribution returning only projects where current_stage IN (M1..M5). The 'awaitingGen / NOT STARTED → Generate Packages' card should only show for projects at M1 with zero packages, not every seed idea.

### [MEDIUM] Gate B/C 'not generated yet' early-return leaves stale loading-pill replaced but skips the captions/emails-missing CTA reachability when fetch returns empty array vs object
**bug** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html renderGateBBlock / renderGateCBlock empty-array guards
renderGateBBlock fetches /api/projects/:id/captions which returns a raw array (projects.js:230-237, res.json(captions)). The guard `if (!captions || captions.length === 0)` then rebuilds innerHTML and returns. That path is fine. However renderGateCBlock guards emails identically, but the M1 dashboard's pending-queue logic in renderDashboard only routes a project to Gate B when `gate_a_approved && !gate_b_approved` and to Gate C when `gate_b_approved && !gate_c_approved` — there is no state for 'gate_a approved but no packages/captions/emails generator has run yet'. A project sitting at M3 with Gate A approved but captions never generated correctly shows the 'Generate Captions in CaptionΩr' CTA, but a project where the M3/M4 generator partially wrote rows then failed is not detected. Low data-loss risk but the gate cannot distinguish 'not generated' from 'generation failed mid-write', so the creator sees a misleading 'not yet generated' message over partial content.
**Fix:** Have the captions/emails GET endpoints (or the generator) record a generation_status on pipeline_state so the gate can show 'generation in progress / failed — regenerate' distinctly from 'not started'. At minimum, surface count mismatches (e.g. captions exist but fewer than clip count) rather than silently treating any non-empty array as complete.

### [MEDIUM] Approve actions are not idempotent / not guarded against double-click; no optimistic-lock, and loadDashboard refetch can re-show an approved gate mid-transition
**bug** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html approveGateA/approveGateB/approveGateC
approveGateA/B/C fire POST then call setTimeout(loadDashboard, 1200). The approve buttons have no disabled state during the in-flight request, so a double-tap (common on the creator's touch workflow) fires two POSTs. db.approveAllCaptions/approveAllEmails/selectPackage are idempotent at the SQL level (UPDATE ... =1), so no corruption — but selectPackage with a second different package_number between clicks would silently change the locked selection with no warning, and the success overlay shows whichever pkgNum was in pendingSelections at click time. Also, because the DB write and the 1200ms refetch are racy with WAL, a fast creator could approve Gate A, see the overlay, then loadDashboard re-renders the same project at Gate B with a fresh loading spinner — there's no in-place advance, the whole queue re-fetches and reflows, losing scroll position. On a long queue this is jarring and can feel like the approval 'didn't take'.
**Fix:** Disable the approve button + show inline spinner on click (re-enable on error). After a successful POST, advance that single block in place to its next gate state instead of setTimeout(loadDashboard) full reload — preserves scroll and removes the race. Guard selectPackage server-side against re-selecting once gate_a_approved=1 (return 409) so a stray second click can't silently re-lock a different package.

### [MEDIUM] No way to REJECT / send back at any gate — only approve or regenerate; breaks the Prime Directive recovery path
**inter-tool** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html (all three gate blocks — action-row only has approve + regenerate)
Every gate offers only '✓ APPROVE' plus (for B/C) a '↻ Regenerate in CaptionΩr/MailΩr' link. There is no 'reject / not yet / kick back to editing' action. If the creator looks at the picture-locked video's packages and decides the EDIT is wrong (not the packages), GateΩr has no affordance to send the project back to ComposΩr/EditΩr — they must leave the dashboard and manually hunt for the prior stage. The Prime Directive asks 'if this goes wrong, how do they get it back?' At M1 the answer is currently 'navigate away and figure it out yourself.' Gate A's note field only feeds the generation phase, it cannot express 'reject'. This makes the gate a one-way ratchet, which is risky for the very first distribution decision.
**Fix:** Add a 'Send back' / 'Hold' action to each gate that clears the relevant gate flag (or sets a held status) and routes the project to the prior stage, with a note. Even a minimal 'Hold for re-edit' that flips current_stage back and surfaces a reason restores the recovery path the Prime Directive requires.

### [LOW] Package card grid uses a fragile string-injection hack to span the odd last card, easy to break on edit
**bug** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html renderGateABlock gridHtml loop
In renderGateABlock the package card is built with `class="package-card${isLast && packages.length % 2 !== 0 ? '" style="grid-column:1/-1' : ''}"` — it closes the class attribute and opens a style attribute mid-interpolation. It currently produces valid HTML for the odd-last case, but it's an unreadable hack: any future edit to that line (adding a class, reordering) will silently produce a malformed attribute and a broken card with no error. It also only special-cases the LAST odd card; if packages ever returns a number other than 5 the spanning logic is brittle.
**Fix:** Build the card with a normal class list and conditionally add a separate CSS class (e.g. 'span-full') applied via classList, instead of splicing attribute boundaries inside the template literal: `<div class="package-card${isLastOdd ? ' span-full':''}" id=... onclick=...>` with `.package-card.span-full{grid-column:1/-1}` in CSS.

### [LOW] Gate naming (A/B/C) is internal jargon that doesn't map to the creator's mental model or the M1-M5 nav labels
**workflow-order** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html gate-badge labels + approved-overlay text vs nav.js:77 'GateΩr M1'
The nav labels this tool 'GateΩr M1', and the pipeline is documented as M1(approve)→M2(package)→M3(caption)→M4(mail)→M5(post). But inside the dashboard the gates are labeled 'GATE A · PACKAGES', 'GATE B · CAPTIONS', 'GATE C · EMAILS' and the overlays say 'advancing to M3 / M4 / M5'. So one screen mixes two numbering systems (A/B/C and M-stages) for the same three steps, and 'GateΩr M1' actually contains Gate A which advances to M3 — there is no Gate that corresponds to the M1 label the creator clicked. For a non-coder creator scanning quickly on a non-filming day, this is a needless cognitive tax and makes the 'reduce decisions' directive harder to meet.
**Fix:** Pick one vocabulary. Either drop the A/B/C entirely and label the three steps by what they are ('Pick Package', 'Approve Captions', 'Approve Emails') with the M-stage as a small subscript, or align the badges to the M-numbers the rest of the system uses. Remove the implication that GateΩr=M1 when it actually walks the creator through what the docs call M2-M4 approval points.

### [LOW] Every gate block's header HTML is duplicated 2-3 times (loading state + each render branch), inviting drift
**simplification** | C:\Users\18054\kre8r\public\m1-approval-dashboard.html renderGateABlock / renderGateBBlock / renderGateCBlock
renderGateABlock/B/C each write the identical title-row + gate-badge header markup in the initial loading innerHTML, then re-write the same header again in the success branch, and (for B/C) a third time in the empty/not-generated branch. That's the same 6-line block repeated up to 3x per function across 3 functions. Any style or label change must be made in ~7 places; gate-6's badge relabel, for instance, would have to be edited everywhere or it drifts.
**Fix:** Extract a single `gateHeader(project, gateLetter, gateLabel)` helper returning the title-row + badge string, and reuse it in all branches. Reduces the relabel/edit surface to one function and removes the divergent-copy risk.
