**POST-MORTEM SYNTHESIS — Learning Loop**

Session 91 wired the post-mortem brief INTO Id8Ωr and WritΩr (closing CLAUDE.md known-issue #5). The loop now *transmits*. But the review confirms the injection was wired without the guardrails that make a steering signal safe — and I verified all six defects are still present in the current code.

**TOP 3 (ranked by blast radius on the creative thread):**

1. **PM-1 (HIGH) — The brief is permanent and invisible.** `getActivePostMortemBrief()` injects into every Id8Ωr and WritΩr call forever with no `created_at` age check, and NorthΩr's persistent banner only surfaces the VectΩr brief — never the post-mortem one. Confirmed at id8r.js:510-518 and writr.js:496-504: zero age logic, while the VectΩr path right above it (id8r.js:498) computes `ageHours` and labels staleness. So a diagnosis from video N silently steers video N+4's script with no on-screen indication Jason is being constrained. This is the Prime Directive violation: a hidden constraint shaping output, no visible recovery path.

2. **PM-5 (MED, but loop-poisoning) — A parse failure silently locks a stub brief.** Confirmed at postmortem.js:213-214: if Opus returns non-JSON, the fallback is `{ root_cause: cleaned.slice(0,200), adjustments: [], avoid: '' }`, and line 216 inserts it as the new ACTIVE brief — superseding the prior good one. The UI shows "✓ locked." A garbled brief now steers the loop AND the previous valid lesson is gone. This is the single most direct corruption of the learning signal.

3. **PM-2 (MED) — The adjustments collapse into mush at the injection point.** Confirmed at id8r.js:514 and writr.js:500: `${pm.adjustments}` coerces the array via `.join(',')`, turning three distinct actions into one comma-spliced run-on line. The UI renders these correctly as bullets (northr.html:4108) — so the model receives a degraded version of the loop's most load-bearing payload. Cheapest high-value fix of the set.

**VERDICT: Functional, but not yet trustworthy.**

The loop is now *wired and transmitting* — Session 91's core achievement is real, and that's the hard part. But it is not yet *safe to trust*, because every one of the three failure modes that matters degrades the signal silently with no recovery path:

- It can't expire or be seen (PM-1)
- It can be silently replaced by garbage (PM-5)
- It arrives garbled even when valid (PM-2)

A learning loop that can't surface, can't expire, and can self-poison without warning is a loop that *runs* but doesn't *learn reliably*. The verdict is **conditionally functional**: the wiring is done, but ship the three guardrails before relying on it — they are small, targeted, and turn a transmitting loop into a trustworthy one. Order: PM-2 (one-line formatting fix ×4 sites), PM-5 (don't supersede on parse failure or empty brief), PM-1 (surface + age-stamp + one-click clear). PM-3/4/6 are follow-ups, not blockers.

## Findings (6 total)
### [HIGH] Post-Mortem brief never expires and is invisible on NorthΩr — silently steers every Id8Ωr/WritΩr call forever
**workflow-order** | src/routes/id8r.js:508-516, 695-706; src/routes/writr.js:493-504, 1003-1012; src/db.js:6179-6186; public/northr.html:3510-3531
getActivePostMortemBrief() returns the single 'active' brief, and insertPostMortemBrief() supersedes the prior active one (src/db.js:6163-6190). Once locked, that brief injects into EVERY Id8Ωr concept/research call (src/routes/id8r.js:508-516, 695-706) and EVERY WritΩr script + Room call (src/routes/writr.js:493-504, 1003-1012) indefinitely — there is no created_at age check anywhere on the injection path. Compare: VectΩr's Studio Intel injection computes ageHours and labels stale briefs (id8r.js:498, 'over 30 days old' warning in northr.html:3813), and the VectΩr active-brief banner shows locked_date. The post-mortem brief has none of that. Worse, the persistent active-brief-banner on NorthΩr (northr.html:3510 loadActiveBrief → only fetches /api/vectr/brief/active) NEVER surfaces the post-mortem brief. So Jason can lock a diagnosis from one underperforming video, and three weeks of WritΩr scripts get steered by 'AVOID this pattern' with zero visible indication it's happening. This violates the Prime Directive's spirit (he's lost track of creative state — a hidden constraint is shaping output) and the Secondary Directive in reverse: instead of reducing decisions it injects a stale invisible one. For a 725k/54k creator doing weekly post-mortems, the brief from video N is still steering when video N+4 ships.
**Fix:** (1) Surface the active post-mortem brief on NorthΩr's persistent banner alongside the VectΩr vector, with its locked date, so Jason always knows it's steering his tools. (2) Add a staleness signal: stamp the injection with brief age ('locked 18 days ago') in the prompt blocks, and ideally auto-expire or visually flag briefs older than ~14-21 days (a post-mortem insight from a month-old video is rarely still the right constraint). (3) Make 'Clear Brief' reachable without re-opening the exact video — e.g. a one-click clear on the banner. This is the difference between a tool that changes what Jason creates next (good) vs. one that quietly distorts it long after the lesson is stale.

### [MEDIUM] adjustments[] array interpolated into prompts as comma-joined string, losing structure
**bug** | src/routes/id8r.js:514, 703; src/routes/writr.js:500, 1009
getActivePostMortemBrief() and insertPostMortemBrief() JSON.parse adjustments into a real array (src/db.js:6174, 6184). But every injection site interpolates it directly into a template string: `Adjustments: ${pm.adjustments}` (id8r.js:514, 703; writr.js:500, 1009). JS coerces an array in a template literal via Array.prototype.join(','), so ['Tighten the hook to 5s','Lead with the dollar figure','Cut the intro montage'] renders as 'Tighten the hook to 5s,Lead with the dollar figure,Cut the intro montage' — one run-on comma-spliced line. The model still reads it, but the three distinct actionable adjustments (the most load-bearing part of the brief, per the Secondary Directive of concrete next actions) collapse into mush, and any adjustment text containing a comma becomes ambiguous. Note the UI itself does this correctly (northr.html:4108 maps to '• '+a bullets), so the prompt injection is inconsistent with the display.
**Fix:** Guard and format: `if (Array.isArray(pm.adjustments) && pm.adjustments.length) pmBlock += '\nAdjustments:\n' + pm.adjustments.map(a => '- ' + a).join('\n');` at each of the four sites. Preserves the bullet structure the model needs to treat them as separate actions.

### [MEDIUM] VisualΩr enrichment match is fragile: 25-char title-prefix substring + arbitrary first-match
**bug** | src/routes/postmortem.js:256-276
In the chat route, the VisualΩr block matches the current video to analyzed-frame results by lowercasing the title and taking the first 25 chars as a substring needle: titleSnippet = title.toLowerCase().slice(0,25), then visResults.find(v => v.title.toLowerCase().includes(titleSnippet)) (src/routes/postmortem.js:262-263). Two failure modes: (a) Titles sharing a 25-char prefix — common for a creator with series/branded openers like 'How We Built Our Off-Grid ...' — will cross-match, attaching the WRONG video's frame analysis to the post-mortem, which then feeds a confidently-wrong visual diagnosis into the conversation and the locked brief. (b) If the title is shorter than 25 chars or punctuation differs, no match and the (often most valuable) visual data is silently dropped with no indication to Jason. Since this is the one signal the AI can't otherwise see (face presence, retention frames), a silent miss or a wrong-video hit materially changes the diagnosis quality.
**Fix:** Match on a stable key (youtube_video_id / project_id) stored alongside the visual results rather than a title-prefix substring. If only titles are available, require a normalized full-title equality or high-ratio fuzzy match, and when matched, echo a small confirmation in the visualBlock (e.g. 'matched: <title>') so a mismatch is visible. When no match is found, say so explicitly in the prompt rather than silently omitting.

### [MEDIUM] Lock Brief enabled after a single AI turn — can lock a 'brief' from a one-message guess
**improvement** | public/northr.html:4088-4089, 3962, 4012, 4074
pmLockBrief guards only on pmHistory.length < 2 (northr.html:4089), and the lock button is enabled the moment the auto-opener's first response streams in (northr.html:4012, 4074, 3962). The opener is explicitly the AI's 'honest read of the data' BEFORE any dialogue (systemPrompt: 'Open with your honest read of the numbers'; userMessage 'Lead with your honest read of the data', postmortem.js:295,317). So with history = [opener], length is 1 — but after one user reply (length 2+, often just 'yeah') the button locks. The brief prompt itself warns the model that 'the conversation may start with an initial read that gets revised' and to base the brief on the FINAL diagnosis (postmortem.js:194) — but if Jason locks after one exchange there IS no revised final diagnosis, just the first impression the prompt warns against. Because this brief then steers Id8Ωr/WritΩr (see PM-1), a premature lock propagates a shallow guess into weeks of content. Violates the Secondary Directive: locking should require enough dialogue that the decision is earned, not a default-enabled button.
**Fix:** Gate the lock on a real diagnosis signal: require at least 2-3 user turns (not just total messages), and/or have the chat route emit a 'diagnosis_ready' flag (the system prompt already says 'Suggest locking a brief when the diagnosis is solid' — surface that as a structured signal that enables the button) rather than enabling it on the first streamed token.

### [LOW] Brief-generation JSON parse fallback can silently lock a malformed/empty brief
**bug** | src/routes/postmortem.js:210-222
In POST /brief, if Opus returns non-JSON, the catch falls back to `parsed = { root_cause: cleaned.slice(0,200), adjustments: [], avoid: '' }` (postmortem.js:213-214) and proceeds to insert it as the new ACTIVE brief, superseding the prior one (db.js:6165). Result: a parse failure produces a brief with a truncated root_cause, zero adjustments, and empty avoid — which then becomes the active steering signal for Id8Ωr/WritΩr, while having wiped the previous (good) active brief. The UI shows '✓ Post-Mortem Brief locked' (northr.html:4112) with no indication the content is degraded. Given the Prime Directive (never lose creative state), silently superseding a good brief with a parse-failure stub is the wrong default.
**Fix:** If JSON.parse fails OR the parsed brief has empty adjustments AND empty avoid, do NOT supersede the existing active brief — return an error so the UI can surface 'couldn't structure the brief, try locking again' and the prior brief stays intact. Only call insertPostMortemBrief on a well-formed result.

### [LOW] Post-Mortem and VectΩr both inject 'Avoid' constraints with no coordination or conflict surfacing
**inter-tool** | src/routes/id8r.js:477-516; src/routes/writr.js:455-504
Both the VectΩr strategic brief (id8r.js:477-491, b.avoid) and the Post-Mortem brief (id8r.js:508-516, pm.avoid) inject independent 'Avoid' directives into the same Id8Ωr concept prompt, and WritΩr layers the post-mortem on top of its own id8rBlock. There is no logic detecting when they conflict (e.g. VectΩr vector says 'double down on lifestyle' while a post-mortem says 'avoid lifestyle framing — it underperformed'). For Jason on a non-filming strategy day, the tools can quietly pull concept generation in opposite directions with no signal that two locked briefs disagree. This is a workflow-coherence gap rather than a crash, but it's exactly the kind of hidden contradiction that makes a strategy tool generate data/output Jason can't act on confidently.
**Fix:** When both an active VectΩr brief and an active Post-Mortem brief exist, surface them together (in the NorthΩr banner per PM-1) and consider a lightweight reconciliation note in the prompt ('Note: strategic vector and last post-mortem may tension on X — prioritize the vector / flag the conflict'). At minimum make both visible simultaneously so Jason notices the contradiction.
