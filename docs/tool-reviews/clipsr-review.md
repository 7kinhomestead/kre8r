# ClipsΩr Review — Synthesis

## Top 3 by Creator Impact (for a 725k TikTok creator)

### 1. The approved caption/hook/hashtags die at the DaVinci boundary — PostΩr re-writes them from scratch
*(clipsr-it-01, CLP-1 — critical, the single biggest waste)*

ClipsΩr's entire reason to exist is producing ready-to-post per-clip metadata (caption, hook, hook_overlay, hashtags, platform_fit, why_it_works) in Jason's voice. The creator can edit and approve these inline. But the handoff to PostΩr is filesystem-only: clips get rendered out of DaVinci into a watched folder, land as NEW `footage` rows with `shot_type='social-clip'`, and have **no foreign key back to the originating `viral_clips` row**. PostΩr's campaign builder (`getUnpackagedClips`, db.js:2817) then calls `/campaign/generate-captions` and writes a brand-new caption via Claude. **The caption Jason wrote, edited, and approved never gets read.** The captioning decision is made twice and his edits silently evaporate.

This is *the* reason ClipsΩr is "a tool he wants to use but can't" — it produces a beautiful artifact that doesn't survive the one step that matters. **Fix:** embed `viral_clip.id` (or `footage_id+rank`) in the `clip-markers.py` timeline/render filename slug; when the watcher ingests a `social-clip`, parse the slug and write `source_viral_clip_id` onto the new row; `getUnpackagedClips` LEFT JOINs `viral_clips` so PostΩr pre-fills the approved caption/hook/hashtags. One continuous thread.

### 2. The vertical/auto-reframe output a TikTok creator actually needs is built but unreachable; the wired path is pure manual labor
*(CLP-3, clipsr-it-02, clipsr-5 — high)*

`create-social-clips.py` (282 lines: pre-trimmed 9:16 1080×1920 timelines + Smart Reframe per clip) is fully orphaned — no route calls it. The wired path, `clip-markers.py`, only drops markers on the full **horizontal** source and makes the creator open Resolve, find each `CLIP_XX` timeline, grade, manually reframe to 9:16, export, and wait for re-ingest — 6+ manual steps per clip, daily. **The currently-shipped path produces *more* manual work than the abandoned one**, directly violating the Secondary Directive. For a daily-posting creator, DaVinci shouldn't be on the critical path at all for a talking-head clip. **Fix:** add a server-side ffmpeg "Quick Export" (`-ss/-to` + center-crop/saliency 9:16 reframe, write straight to `[project]/clips/` with `viral_clip_id` in the filename — this also feeds fix #1). DaVinci becomes the optional power-path for clips needing real grading. Delete or consciously retire `create-social-clips.py`.

### 3. Re-analyze hard-deletes approved clips and all hand-edits with no warning
*(clipsr-4, CLP-6 — Prime Directive violation)*

`POST /analyze` step 3 unconditionally calls `deleteViralClipsByFootage(footage.id)` before inserting the new set — wiping **all** rows including `status='approved'` clips and any hand-tuned caption/hook/hashtags/why_it_works. The frontend exposes a `🔄 Re-analyze` button (`startAnalysis(id, true)`) with no confirmation. One accidental click discards approved creative work that also feeds PackageΩr/MailΩr/Id8Ωr/VectΩr downstream — no warning, no undo. The PUT handler even runs `db.checkpoint()` specifically *so approved clips survive restarts*, yet re-analyze deletes them outright. **Fix:** only delete `status IN ('candidate','skipped')`, dedupe new candidates against approved time ranges, and gate behind a confirm naming how many approved clips would be lost.

**Honorable mention worth fixing cheaply:** `hook_overlay` (AI-generated on-screen text, max 8 words) is **never persisted** — missing from the `viral_clips` schema, `insertViralClip`, and the PUT allowlist, so the Text Overlay box is always empty after reload (clipsr-10, clipsr-it-06). And the **overlap-dedup walks clips in rank order, not start-time order** (CLP-2, clipsr-3), so non-overlapping strong clips get silently dropped — a 17–33% output reduction on a 3–6 clip run with only a `console.warn`. Both are high-leverage, low-cost.

## WORKFLOW ORDER VERDICT

**ClipsΩr must sit AFTER ComposΩr, and PostΩr must consume ClipsΩr's output directly.**

Correct order: `ReviewΩr → ComposΩr → ClipsΩr → PostΩr`

The nav (`public/js/nav.js:57-65`) currently orders it `AssemblΩr → ReviewΩr → ClipsΩr → ComposΩr → BrollΩr` — **ClipsΩr before ComposΩr** — which contradicts CLAUDE.md's canonical pipeline *and* the tool's own data dependency. This is not cosmetic and it's actively harmful:

- ClipsΩr hard-filters `shot_type='completed-video'` (clipsr.js:60). A video is only "completed" after ComposΩr finishes color/audio/final render. At its current nav position the creator hits ClipsΩr and finds an **empty list** ("No completed videos") — the literal "tools he wants to use but can't" complaint.
- If a creator *did* clip before ComposΩr, they'd be mining a non-final cut. ComposΩr then re-renders, and the clip timestamps no longer match the file — which is exactly the failure the `send-to-davinci` "timestamps exceed duration" guard catches after the fact. **The nav order steers the creator straight into the timestamp-mismatch bug.**

**Fix:** reorder the post group to `VaultΩr → AssemblΩr → ReviewΩr → ComposΩr → ClipsΩr → BrollΩr → AnimΩr → CleanΩr`. The visual flow then *teaches* the correct order: finish the video, then mine it for clips. This also removes a decision ("clip now or wait?") — ClipsΩr only appears once a final video exists, which is the only state where its list is even populated.

### [HIGH] send-to-davinci silently produces empty clip transcripts when transcript lives only in DB column
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\routes\clipsr.js:~210-225 (transcriptSegments load) and clipTranscript() at ~227-233
**Problem:** POST /api/clipsr/send-to-davinci builds per-clip transcript text ONLY from footage.transcript_path (the on-disk JSON with segments). But the analyze flow can complete using just the DB 'transcript' text column with no transcript_path set: in the analyze handler, when footage.transcript exists it is parsed/used directly and transcript_path is never required. transcribeFile only writes transcript_path when it actually runs (skipped/cached paths do set it, but the 'existing && !force_retranscribe' branch reads footage.transcript text and never backfills transcript_path if only the text column was populated by an earlier non-ClipsΩr ingest). When transcript_path is absent or the file is gone, the code at line ~225 silently swallows the failure (catch(_) {} ) leaving transcriptSegments = []. clipTranscript() then returns '' for every clip, so DaVinci timelines are created with no transcript context in the marker notes/payload. No warning surfaces to the creator — the clips still 'send' but lose the per-clip caption/context the workflow promises.
**Fix:** When footage.transcript_path is missing/unreadable, fall back to reconstructing segments from the same transcript object the analyze step loaded (DB transcript JSON), or look up the slug-based file via transcriptSlug(footage.file_path). At minimum, log a pino warning and include a flag in the response so the UI can tell the creator transcript context was unavailable rather than failing silently in catch(_){}.

### [HIGH] Overlap dedup walks clips in RANK order, not start-time order — overlapping clips can slip through
**Dimension:** bug | **Location:** C:\Users\18054\kre8r\src\vault\clipsr.js:170-178
**Problem:** In src/vault/clipsr.js the overlap dedup loop (lines 170-178) assumes clips are ordered by start time: it compares clip.start < prev.end against only the immediately-preceding element.
