## CRITICAL

**C1. Field marks silently revert on auto-refresh — coverage state lost (SD-1 + SD-5-html)**
`fetchBeats()` runs every 10s and the server-authoritative merge overwrites any locally-marked beat whose POST failed. The catch block promises "will retry on next refresh" but no retry queue exists — the refresh does the opposite and restores the stale `needed` state. On flaky field WiFi, a creator marks a beat GOOD, sees the toast, and 10s later it flips back to NEEDED with no recovery. Direct Prime Directive violation.
→ *Fix: pendingWrites set; re-POST before merge; never let server `needed` overwrite an unsynced local mark.*

**C2. take_number increments on GOOD and SKIP — counts corrupt and client/server disagree (SD-2 + SD-4)**
*Confirmed `src/db.js:4420-4422`:* any non-`needed` status increments. Skipped beats show "Take 1+". The live frontend only increments on `good`; the offline package increments on `skip` too — three code paths, three rules. After each refresh the over-counted server value clobbers the client. The one number that justifies the tool over a paper script lies, and AssemblΩr reads it downstream.
→ *Fix: increment only on `good`; make server authoritative; mirror in both frontends; add skip→good→again == 2 test.*

**C3. Beat reorder/edit between sessions orphans all takes — marks bind to wrong beats (SD-3 + SD-6 + ST-3)**
shoot_takes is keyed by positional `beat_index` with a `(i+1)` fallback, but WritΩr beat builders inconsistently emit an `index` field. Re-running WritΩr (add/remove/reorder a beat) leaves every take bound to its old slot, so take #3 lands on whatever beat now sits in position 3. The creator returns to a half-finished shoot and sees GOOD marks on the wrong beats, silently. Also a latent hazard the moment anyone joins shoot_takes→AssemblΩr by index.
→ *Fix: key takes by a stable beat id/slug carried through PipΩr→WritΩr→ShootDay→AssemblΩr; until then, detect beat-list drift and warn instead of re-binding by position.*

## TOP 3 BY CREATOR IMPACT

1. **Coverage marks silently revert on refresh (C1).** The creator can mark a beat GOOD, get confirmation, and have it flip back to NEEDED 10 seconds later on field WiFi — with a "will retry" promise the code never keeps. This is the purest violation of "never lose creative state," and it strikes during the live shoot when there's no second chance.

2. **The field log never reaches the edit (H1 / H3).** Everything the creator marks during the shoot — every GOOD, every SKIP, every note, and everything Cari captures on the offline package — is invisible to AssemblΩr. The tool's entire downstream payoff is fictional; a doc even asserts a feedback loop that the code does not implement. The marking labor is spent for nothing beyond ShootDay's own UI.

3. **Take counts and beat identity are corrupt (C2 + C3).** The take counter increments on skips and undos, so "Take 3" can mean a beat shot once — destroying trust in the one number that beats a paper script. And because takes key on unstable positional indices, re-editing the script between sessions silently re-binds GOOD marks to the wrong beats. Together they make the coverage map untrustworthy exactly when the creator relies on it most.

## VERDICT: Does ShootDay earn its place for a solo outdoor creator?

**Not yet — but the concept is sound and the gaps are closable.** The premise is exactly right for this creator: fuse the script with live coverage so a solo creator in a 700-sq-ft outdoor space, partner on camera, knows what to say, what to shoot, and what's left — without an admin layer. That is genuine pipeline value a paper script cannot match.

But **as built, ShootDay fails its own Prime Directive in the field and delivers none of its downstream promise.** Field marks can vanish on refresh (C1), the offline package — the device most likely used outdoors — is a one-way data sink (H3), and the entire coverage log never reaches the edit (H1). Meanwhile the highest-leverage intelligence WritΩr already computed (the anchor shot, the exact b-roll to capture, the true coverage gaps) is whitelisted out before it ever reaches Cari's phone (H2), and the counts/identity the creator relies on are corrupt (C2, C3). Today a careful creator is *safer with a paper script*, because paper doesn't silently revert.

**The verdict is conditional-keep.** ShootDay earns its place the moment three things are true: (1) field marks survive flaky networks with a real retry/pending-write path, (2) the field log — online and offline — actually reaches AssemblΩr, and (3) WritΩr's anchor/coverage/missing-beats data flows through to the shot card. Those three changes (C1, H1+H3, H2) convert it from a risk into the highest-value screen in the post-production handoff. Until then it is a promising tool that quietly loses the creative thread it was built to protect.

## Full Findings (36 total)
### [CRITICAL] Skip mark silently reverts on next auto-refresh — coverage state lost mid-shoot
**Dimension:** bug | **Location:** public/shootday frontend, markTake() catch block (showToast 'will retry on next refresh') + fetchBeats() merge loop `if (b.status !== 'needed' || b.take_number > 0)`
**Problem:** fetchBeats() runs every 10s. Its server-merge rule (frontend) is: `if (b.status !== 'needed' || b.take_number > 0) { takes[b.index] = server }`. When the creator marks a beat 'skip', upsertShootTake increments take_number to >=1 so this normally survives. BUT the offline package and the live app diverge here, AND the deeper issue: a beat marked 'skip' has status='skip' and take_number>=1 on the server, so server overwrites local — fine. However if a POST fails (showToast 'Save failed — will retry on next refresh') the local 'good'/'skip' is held ONLY in JS memory with NO retry queue. The comment promises a retry that does not exist: fetchBeats does the OPPOSITE — it overwrites the unsaved local mark with the stale server 'needed' state on the very next 10s refresh. In the field on flaky WiFi this means a creator marks a beat GOOD, sees the toast, moves on, and 10 seconds later the beat silently flips back to NEEDED. Coverage state is lost with no recovery path. Directly violates the Prime Directive.
**Fix:** Implement the promised retry queue: on POST failure, keep the unsaved mark in a pendingWrites set and have fetchBeats() NOT overwrite any beat that has a pending local write. Re-POST pending writes at the top of each refresh before merging server state. Never let a server 'needed' overwrite an unsynced local 'good'/'skip'.

### [CRITICAL] take_number increments on every GOOD and SKIP — and on SKIP, which is semantically wrong and corrupts counts
**Dimension:** bug | **Location:** src/db.js:4420-4422 (upsertShootTake increment logic) vs frontend markTake() newTakeNum computation
**Problem:** db.upsertShootTake increments take_number for ANY status that is not 'needed': `newTake = status === 'needed' ? existing.take_number : existing.take_number + 1`. Two problems: (1) Marking a beat 'skip' increments the take counter, so a skipped beat shows 'Take 1' (or higher) even though nothing was shot — misleading in Review and the crew log. (2) The frontend markTake() ALSO maintains its own counter: `newTakeNum = status === 'good' ? prev.take_number + 1 : prev.take_number` (skip does NOT increment client-side). So client and server disagree on take_number for every skip and every undo. After the next fetchBeats the server value (which over-counted) clobbers the client value. Take counts shown to the creator are unreliable.
**Fix:** Only increment take_number when status === 'good'. Make the server authoritative and remove client-side counting, OR send the desired take_number from the client. Align the two rules so skip/undo never change the take count.

### [CRITICAL] WritΩr beat reorder/edit orphans all existing takes — coverage map silently shifts to wrong beats
**Dimension:** bug | **Location:** src/routes/shootday.js buildBeatList() `const idx = b.index != null ? b.index : (i + 1)` + src/routes/writr.js:1279 storyboard beats lacking index
**Problem:** shoot_takes rows are keyed by beat_index. In buildBeatList the index is `b.index != null ? b.index : (i + 1)` — i.e. positional fallback (1-based) when WritΩr beats lack an `index` field. WritΩr produces beat_map_json from MULTIPLE builders: the marker parser (writr.js:1135) assigns index:i+1, the storyboard builder (writr.js:1279) sets name/beat_name but the object has NO index property, and room-revision reuses prior maps. So whether a beat carries a stable `index` is inconsistent. If the creator re-runs WritΩr / re-approves a script that adds, removes, or reorders a beat BETWEEN shoot sessions, every shoot_takes row stays bound to its old numeric beat_index. Positional fallback then maps take #3 onto whatever beat now sits in position 3 — a DIFFERENT beat. The creator returns to a half-finished shoot and sees GOOD marks attached to the wrong beats, with no warning. This is silent creative-state corruption.
**Fix:** Key takes by a stable beat identifier (beat slug/hash of name, or persist a stable beat id from WritΩr) rather than positional index. At minimum, detect when the beat list length/names changed since takes were recorded and warn the creator instead of silently re-binding by position.

### [HIGH] Offline package and live app use different, non-synced take stores — field divergence
**Dimension:** bug | **Location:** src/routes/shootday.js generateOfflineHTML() STORAGE block (STORE_KEY = 'sd_'+PROJECT.id, localStorage only) vs live markTake() POST to /take
**Problem:** The offline HTML package stores takes ONLY in localStorage under key 'sd_'+PROJECT.id (route generateOfflineHTML: loadTakes/saveTakes), while the live app stores via /take API in shoot_takes AND its own localStorage 'kre8r_sd_project'/'kre8r_sd_prefs'. There is no sync path between them. The documented field workflow is: Cari uses the offline package on her phone (no network) while the shoot happens. Every take she marks lives only in her phone's localStorage and is NEVER written back to the DB. AssemblΩr/EditΩr read shoot_takes downstream (per CONNECTIONS) — so the entire shoot-day coverage log captured on the offline package is invisible to post-production. The creator believes coverage was logged; the edit sees zero takes.
**Fix:** Give the offline package an export/sync action (e.g. 'Sync takes to server' that POSTs the localStorage take map to /take when back online), or at minimum surface clearly that offline takes are local-only and must be re-entered. Best: a bulk reconcile endpoint the package calls on reconnect.

### [HIGH] POST /take has no project-existence guard — creates orphan takes for any integer id
**Dimension:** bug | **Location:** src/routes/shootday.js POST /:project_id/take handler (no db.getProject check before db.upsertShootTake)
**Problem:** POST /:project_id/take validates only that projectId parses truthy and that beat_index/status are present. It never calls db.getProject to confirm the project exists (unlike /beats, /crew-brief, /package which 404 on missing project). It writes directly via upsertShootTake. A stale localStorage 'kre8r_sd_project' pointing at a deleted/renamed project (common given the CLAUDE.md note that Electron DB and source DB assign DIFFERENT ids to the same project) will silently accumulate takes under a phantom project_id. The creator marks beats GOOD all day; the takes are real DB rows but bound to a project the rest of the pipeline doesn't load. Coverage appears to save but is unreachable.
**Fix:** Add `if (!db.getProject(projectId)) return res.status(404).json({ error: 'Project not found' });` at the top of the /take handler, mirroring the other routes. The frontend should clear stale kre8r_sd_project and reopen the selector on 404.

### [HIGH] Beats with no stable index collapse onto beat_index 1 when WritΩr beats lack index AND order is unstable
**Dimension:** bug | **Location:** src/routes/shootday.js GET /:project_id/script (`const beats = script.beat_map_json || script.beat_map || config?.beats`) vs buildBeatList() source selection
**Problem:** buildBeatList computes idx from positional fallback, but the /script endpoint and the offline package compute beat index INDEPENDENTLY: route /script does `b.index != null ? b.index : (i + 1)` over `script.beat_map_json || config?.beats`, while /beats does the same over the WritΩr-vs-PipΩr merged list which may have a DIFFERENT length or source than /script. If WritΩr beat_map is non-empty (wins in /beats) but the /script endpoint falls back to config.beats (different count), the Script tab's beat dots and the Shots tab refer to different beat numbers for the same logical beat. refreshScriptDots() then lights the wrong dots, and TeleprΩmpter sync (syncScriptPosition) highlights the wrong beat. The two tabs disagree about what 'Beat 3' is.
**Fix:** Make /script and /beats derive their beat list from the SAME buildBeatList() output so indices are guaranteed identical across tabs. Do not let /script independently fall back to a different source.

### [MEDIUM] saveNote sends status 'needed' default which can DOWNGRADE a beat and reset take_number semantics
**Dimension:** bug | **Location:** src/routes/shootday.js frontend saveNote() — `status: takes[idx].status || 'needed'` POST body
**Problem:** In the live frontend saveNote(): if no take exists it creates `{ status: 'needed', ... }` then POSTs with `status: takes[idx].status || 'needed'`. If the creator opens the note dialog on a beat that was already marked 'good' on the SERVER but whose local take object got reset (e.g. after changeProject clears takes={} but project stays, or after a failed fetch), saveNote will POST status:'needed' for that beat, overwriting the server 'good' with 'needed'. upsertShootTake on 'needed' does not increment but DOES set status='needed', wiping the GOOD coverage mark — just by adding a note. Adding a director's note should never be able to un-cover a beat.
**Fix:** saveNote must preserve existing server status. Either fetch current status first, or add a note-only DB path that updates note without touching status/take_number. Never POST a default 'needed' status from the note flow.

### [MEDIUM] shot_type inference for talking_head misclassifies covered-by-broll beats as Talking Head in field UI
**Dimension:** bug | **Location:** src/routes/shootday.js buildBeatList() shot_type ternary (default 'talking_head') + buildShotCard isTH logic
**Problem:** buildBeatList infers shot_type: `b.shot_type || (b.talking_head_prompt ? 'talking_head' : (b.coverage_footage_ids?.length ? 'broll' : 'talking_head'))`. The default-of-last-resort is 'talking_head'. WritΩr beats frequently have neither shot_type nor talking_head_prompt nor coverage_footage_ids (the marker/storyboard builders only set index+beat_name+story_moment). So genuine b-roll/action beats are labeled 'Talking Head' on Cari's card, and shotTypeLabel/typeLabel show the wrong badge. In the field this tells the camera operator to shoot a piece-to-camera for a beat that should be silent b-roll — a wrong-coverage error that surfaces only in the edit.
**Fix:** Default ambiguous beats to a neutral 'b-roll' or 'unspecified' label rather than 'talking_head', or carry shot_type explicitly from WritΩr/PipΩr so it is never guessed. A guess that defaults to the most directive shot type is the most dangerous default.

### [MEDIUM] Crew-brief and package PDF/HTML generation has no timeout — a hung python spawn ties up the request forever
**Dimension:** bug | **Location:** src/routes/shootday.js GET /crew-brief/:project_id — `new Promise((resolve, reject) => { const py = spawn(...); py.on('close', ...) })` has no setTimeout/kill
**Problem:** GET /crew-brief spawns python (detectPython + spawn(scriptPath)) and awaits py.on('close') with NO timeout. If python hangs (reportlab waiting on a font, a blocked stdin, an antivirus scan on Windows), the Promise never resolves, the HTTP request hangs, and the creator gets a spinning download with no error. On shoot day a creator generating Cari's brief gets a dead tab. detectPython itself can also block if a python candidate hangs on --version.
**Fix:** Add a watchdog: setTimeout that kills the child (py.kill) and rejects after ~20s. Same for detectPython execFile probes. Return a clear 'PDF generation timed out' error so the creator can fall back to the offline HTML package.

### [MEDIUM] buildBeatList called twice per take POST — double DB read and config file read on every mark
**Dimension:** bug | **Location:** src/routes/shootday.js POST /:project_id/take coverage recompute (`buildBeatList(projectId)?.beats`) + src/pipr/beat-tracker.js readConfig directory-scan fallback
**Problem:** POST /:project_id/take calls db.upsertShootTake, then immediately calls buildBeatList(projectId) again purely to recompute coverage (`const beats = buildBeatList(projectId)?.beats || []`). buildBeatList does getProject + getApprovedWritrScript + readConfig (filesystem read, including the directory-scan fallback in beat-tracker.readConfig when the id path misses) + getShootTakes. On a rapid-fire shoot (Cari tapping GOOD repeatedly), every tap triggers a full project rebuild including a potential fs.readdirSync scan of all project config dirs. Under load this serializes and can make the 'GOOD' button feel laggy in the field; the readConfig fallback scan is O(projects) per tap.
**Fix:** Compute coverage directly from db.getShootTakes(projectId) and a cached beat count instead of rebuilding the full beat list. Cache readConfig per project_id, and avoid the readdir fallback scan on the hot take-POST path.

### [LOW] Offline package localStorage take key has no schema/migration — old packages collide with new beat indices
